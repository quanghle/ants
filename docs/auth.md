# Credentials and ACLs

`ants auth` manages decentralized NATS NKey/JWT credentials in `~/.config/ants/auth` (`--dir` / `ANTS_AUTH_DIR`; keep `*.nk` seeds private):

```sh
ants auth init                                          # writes operator.nk, store.nk, account.nk, system.nk, server.conf
                                                        # (on a team without store.nk: adds it, rewrites server.conf)
ants auth user human --js-domain hub                    # human.creds ("human" always gets Role::Human)
ants auth user alice --human --js-domain hub            # alice.creds (human role, new device ID)
ants auth user alice --human --admin --js-domain hub    # alice.creds (human role and admin role)
ants auth user pa --assistant-of alice --js-domain hub  # pa.creds (ant role, assistant of alice)
ants auth user dev-a --js-domain hub                    # dev-a.creds (ant role)
ants auth builtin messenger --js-domain hub             # system-messenger.creds
ants auth builtin sage --js-domain hub                  # system-sage.creds
ants auth user github --webhook --to dev-a --js-domain hub
ants auth user nightly --webhook --to dev-a --js-domain hub  # schedules use webhook credentials
ants auth channel-manager --js-domain hub               # channel-manager.creds
ants auth host worker-1 --js-domain hub                 # host-worker-1.creds (the machine's daemon)
ants auth user audit --observer --js-domain hub         # audit.creds (read-only, for hooks)
ants auth user alice --human --store-key --js-domain hub  # seed stored in OS credential store
```

## Issuing and revoking credentials

Every key issued or signed (`user`, `builtin`, `enroll`, `bootstrap`, `channel-manager`, `host`, `leaf`, `enroll approve`, `enroll renew`, `signer`) is recorded in `issued.jsonl` (public key, name, kind, issue time, expiry, permissions version, plus device ID/label, GitHub binding and grant, `admin`, `assistant_of`, or leaf members). `ants auth leaf` records its store account uplink (`leaf-<machine>.store.creds`) beside the uplink, under the same name `leaf-<machine>`, as kind `leaf-store`, with the uplink's lifetime (no expiry). Built-in credentials have the normal rights of an ant under the reserved service ID; `ants auth user` cannot issue them. Credentials stay valid until expiry unless revoked:

```sh
ants auth revoke alice --nats wss://hub.example/nats        # every key issued to alice, all devices
ants auth revoke --key UABC... --nats wss://hub.example/nats # one public key
ants auth revoke --key UABC... --earlier                    # it and the live keys it was renewed from
ants auth revoke leaf-worker-1 --no-push                    # record in server.conf without pushing yet
ants auth revoked                                           # key, name, revoked at, expiry
ants auth issued [--json]                                   # all issued keys + renewal commands
ants auth admin list [--json]                               # live keys carrying the admin role
ants auth admin drop alice --nats wss://hub.example/nats    # revoke every admin key of alice
ants auth push --nats wss://hub.example/nats                # push account JWT to hub and leaves
```

`ants auth revoke NAME` revokes all keys for `NAME` in `issued.jsonl` (plus matching `.creds` files in `--dir`), updates
`revoked.json` and `server.conf` (revoking JWTs for those keys issued at or before the revocation timestamp while
leaving newer keys valid; a leaf node's store account uplink in the store account's JWT, every other key in the team
account's, and a key `issued.jsonl` does not know in both), and pushes the updated store and team accounts via
`$SYS.REQ.ACCOUNT.<account>.CLAIMS.UPDATE` to close
revoked connections immediately. Revoking `leaf-<machine>` thus revokes the leaf's store account uplink with its
uplink, closing the hub's sourcing of its outbox. Revoking an ant or assistant by name also deletes its identity record from
`ants_identities` once the account is pushed (with `--no-push` the record stays; `--key` and `--device` revocations keep
it). Adding the ant again under the name creates a new record with a new `id`. With the earlier home and built-in
sense, the new record keeps the sense id, avatar, birth and prompts counted before revocation, including during
service and after a daemon crash ([config.md](config.md#avatars), [sense.md](sense.md#identity)). The revoker can
read the final identity record and keep its growth at `growth.<sense-id>` in `ants_identities` before the conditional
delete; only the revoker writes that growth.

Renewing credentials (`ants renew`) leaves the key renewed valid until it expires: `--key K --earlier` also revokes the live keys K was renewed from (`renewed_from` in `issued.jsonl`), and those they were renewed from in turn, so the holder keeps no earlier live key; `ants retire` and a refused retire order print it with the ant's key for a machine without the account key. A revocation that leaves an ant or assistant no live key (by name or `--key`) also drops it from the leaf nodes whose members `issued.jsonl` keeps it among, as a [retire order](#adding-and-retiring-an-ant-by-order) does: for this machine's leaf node (`~/.config/ants/leaf.conf`) it renews the uplink credentials for the same key without what they allowed only for the ant, has the node reconnect its uplink, then drops the ant from the leaf's members in `issued.jsonl` and, unless `--no-push`, from what `ANTS_IN` takes from the machine's outbox. For a leaf node whose uplink credentials are on another machine, or when renewing them fails, it prints `ants auth leaf M --remove-ant ANT` and `ants leaf outbox M --remove-ant ANT` to run instead; the keys stay revoked. Revocations of keys whose credentials have all expired are pruned on the next `revoke` or `push`.

After applying a revocation that leaves an ant or assistant no live key, `ants auth revoke`, `ants retire`,
`ants assistant disable --retire`, and `ants signer` also remove the ant's durable `chan-<ant>` and `done-<ant>`
consumers if the colony shows no live daemon serving it. The inbox consumer stays. Cleanup uses temporary
credentials scoped to that ant and those two consumers. If cleanup was skipped with `--no-push`, or the hub could
not be reached for cleanup, repeat `ants auth revoke --key K` directly against the hub, without `--no-push`, once
the ant is no longer served.

Include `server.conf` on the hub followed by `resolver { type: full, dir: "/ABSOLUTE/DIR" }` so pushed revocations persist across hub restarts and offline leaf nodes catch up within 10 s of reconnecting via their `leaf-<machine>.system.creds` uplink. Without a `full` resolver, copy `server.conf` to the hub and reload (`SIGHUP`) after each revocation. Full hub/leaf resolver mechanics live in [transport.md](transport.md#revocation).

Run `ants init` once with human credentials to create stream `ANTS`, all 21 KV buckets and attachment store `ants_files` (the first connection of any CLI command with human credentials also creates missing objects, after one concurrent round of stream infos). `ants init` only creates, and denies rollups: an object already on the hub keeps its settings, such as the sources `ants leaf outbox` adds, but for its rollups. Every stream and bucket denies rollups (`allow_rollup_hdrs: false`), since one message with a `Nats-Rollup` header to a key a user may write would remove every other entry of the bucket, such as every conductor's trail runs or every ant's tips; a KV bucket, which async-nats creates allowing them, has them denied by a stream update right after its creation, and `ants init` (and the first connection of a CLI with human credentials) denies them on a bucket made allowing them, as by `nats kv add`, its entries kept. `ants doctor` fails its `hub` check for an object allowing rollups, naming `ants init`. `ants_colony` places no expiry markers, which `nats-server` allows only with rollups: a standby daemon times an entry's expiry from its last put instead. Humans therefore update the streams of every bucket they create (`$JS.API.STREAM.UPDATE.KV_<bucket>`). It creates `ANTS`, `KV_ants_colony`, `KV_ants_channels` and `KV_ants_humans` with `max_consumers` `10000` rather than the `1000` `nats-server` gives by default (the buckets by a stream update right after creating them). It writes the incarnation marker of `ants_identities` (`_incarnation`) when absent, which the bucket's shared settings are signed for ([below](#wire-acls-and-verification-invariants)); `ants init --identities-restored` writes it anew after a restore from backup.

## Machine host credentials

`ants auth host MACHINE` issues a machine's host credentials (user `host-<machine>`, never expiring, written to `host-<machine>.creds` in the team directory unless `--out` names another file). The daemon serving a whole config file on that machine connects with them once, apart from its ants, over its own inbox prefix `_INBOX_HOST.<machine>`, and keeps the machine's record in `ants_machines` (`<machine>`: the ants it serves) current: on start, and on each reload that changes them. The record is never deleted, so an ant whose daemon stopped and whose colony entry expired still has a machine (`ants machines`). Sense writes the logs of the machine's ants with them too: over that connection, or, from a daemon serving one ant (`ants daemon --ant`), over a link of sense's own made with them, which writes no machine record, takes no admin orders and writes no shared settings. Without them, where the ants have credentials of their own, sense keeps none of its ants' data: `ants doctor` fails its `sense data` check, and the daemon's log and each such ant's colony entry say why, the ants still served ([config.md](config.md#providers)).

The daemon finds them as the `[host]` table's `creds` ([config.md](config.md)), else `~/.config/ants/auth/host.creds`, else `host-<machine>.creds` there for the table's `machine`, else for the config's top-level `machine` (when it is a machine name) or the first label of the host name, whichever exists; the daemon reloads once one of those files comes, goes or changes ([config.md](config.md#precedence-and-reload)). The machine is the table's `machine`, else the one the credentials name, else the top-level `machine` when it is a machine name, else the first label of the host name; a table naming another machine than its credentials is an error. On the machine holding the team keys, `ants setup` issues them where the daemon finds them once the config file's ants have credentials; elsewhere copy the file to `~/.config/ants/auth/host.creds`, or let `ants add --enroll` ask for them with its ant ([Host credentials over NATS](#host-credentials-over-nats)). Behind a leaf node, the host connects through the leaf's uplink, which allows what the host of the leaf's own machine may do, so the credentials must name that machine.

A host may only put its own record (`$KV.ants_machines.<machine>`), never the `_account` record of the [machine holding the account key](#adding-an-ant), and, for its machine's [admin orders](#admin-orders), look up and create the consumer `admin-<machine>` of `ANTS` filtering `ants.admin.<machine>.>`, take its messages and ack them, put and direct-get their outcomes (`$KV.ants_machines.<machine>.>`) and direct-get the revocation records of `ants_devices` (`revoked.<U...>`); for [add and retire orders](#adding-and-retiring-an-ant-by-order) it also publishes enrollment requests (`ants.enroll.*`), takes their answers (`ants.enroll.*.reply`) and direct-gets colony entries (`$KV.ants_colony.*`); for [an assistant's orders](#an-assistants-orders) it watches `ants_humans` (stream info, direct gets and an ordered consumer, writing none of it) for its humans' grants and consents; for sense, it creates stream `ANTS_SENSE` with the one config every host creates it with, appends to it (`ants_sense.*`) and reads it by direct gets (`$JS.API.DIRECT.GET.ANTS_SENSE`, no stream info or consumer) ([Sense event logs](#wire-acls-and-verification-invariants)); it reads no inbox, channel or other bucket. No ant, webhook, observer or human writes `ants_machines`; humans look it up, create it and read all of it, by batched direct gets alone (`$JS.API.DIRECT.GET.KV_ants_machines`, no consumer). A daemon without host credentials, whose ants have credentials, logs once that the record and the admin orders stay off and serves its ants as before; with no credentials anywhere (a hub without `ants auth`), the host connects as no one. `ants doctor` warns of the missing credentials and names the `ants auth host` command. `ants auth host MACHINE` reissues host credentials (new key, current permissions); they do not renew over NATS.

## Backing up the team keys

Keep an off-machine backup of the team directory (`operator.nk`, `account.nk`, `store.nk`, `system.nk`, `server.conf`, `issued.jsonl`, `revoked.json`; `.creds` files are omitted):

```sh
ants auth backup /media/usb/ants-team.age               # prompts for passphrase twice
ANTS_BACKUP_PASSPHRASE=... ants auth backup team.age    # or --passphrase-file FILE
ants auth restore team.age --dir ~/.config/ants/auth    # --force replaces existing team files
```

A backup made before `ants auth init` added the store account lacks `store.nk` and restores nothing; `ants doctor` warns until a new backup holds it.

Backups use ASCII-armored [age](https://age-encryption.org) passphrase encryption (scrypt work factor 18 + ChaCha20-Poly1305, mode `0600`), compatible with `age -d` and `age -p`. Team keys always stay on disk (never in the OS credential store). `backup.json` records the last backup's issued-key count and revocation digest so `ants doctor` warns when new keys or revocations are unbacked-up. Restoring an older backup loses revocations made since: re-revoke those keys and run `ants auth push`.

## Devices

Each `ants auth user NAME --human` issues credentials with a unique UUIDv7 `ants-device:<id>` JWT tag and optional `--label`; the tag is required on human credentials:

```sh
ants auth user alice --human --label "workstation"
ants auth devices alice [--json]
ants auth rename alice "workstation" "main-workstation" # by unique label, device ID, or public key
ants auth revoke alice --device 01968f7e-...            # revoke one device only
```

`ants auth devices` prints, per device, its ID, label, public key, encryption key and issue time, plus `github LOGIN (grant)` for a device of a name bound to a GitHub user, `admin` for one carrying the [admin role](#admins), and `revoked`; `--json` prints the same as JSON lines (`github`, `grant`, `admin`). Without `--json`, a line `assistant NAME KEY issued TIME [revoked]` follows for each key of the human's [assistant](#assistants).

All devices of a human share its inbox read marker (`<human>`) and its channel read markers (`<human>.chan`) in `ants_read` (CAS-updated) and per-device presence in `ants_presence` for notification suppression (see [webhooks.md](webhooks.md#notifications)) and for showing in `ants chat` which other humans are online.

### Device encryption keys

Each human device also gets an X25519 encryption key (an nkeys xkey, public key `X...`), generated beside its NKey and bound into its user JWT as the tag `ants-xkey:<X...>`, so the account's signature ties it to that human and device. Messages sealed for the device are opened with its seed, which never leaves the device. The seed follows the NKey seed: in the `.creds` file as an `ANTS XKEY SEED` block after the NKey seed (nats tools read only the first two blocks and ignore it), or with `--store-key` in the OS credential store under its public key, the file keeping an `ANTS STORED XKEY` block. Ant, webhook, observer, channel manager and leaf credentials carry none.

```sh
ants auth user alice --human --public-key U... --xkey X...   # sign keys generated on the device; without --xkey none is bound
ants renew ~/.config/ants/auth/alice.creds                  # credentials binding none get a new key
ants login --hub wss://hub.example/nats --name alice       # a registered device gets one too
```

`ants auth devices` lists each device's encryption key (`xkey` in `--json`), as `issued.jsonl` records it.

#### Directory of device keys

Senders find the encryption keys of humans' devices in KV `ants_devices`. On connecting (and on `ants init`), a human's CLI whose credentials bind a key puts their user JWT under `<human>.<device>` when the entry differs (one direct get otherwise), warning without failing when it cannot. A human's credentials may create the bucket, read all of it and put only their own `<human>.>` keys, so no human swaps or drops another's device key; webhooks, observers and the channel manager get no right on it, and ants only the reads below. The user name `revoked` is reserved.

An assistant's daemon also puts its own user JWT there, under `<assistant>.assistant` ([acting for its human](#acting-for-its-human)); ants may direct-get those records and the `revoked.*` ones, nothing else of the bucket.

A reader takes a device's key only from a JWT it verifies itself: signed by the account that signed the reader's own credentials, a human's user JWT named for that human, tagged with that device and binding an `ants-xkey:`, unexpired, and with no `revoked.<U...>` record for its user key. It skips and reports (a warning) every other entry of the humans it reads, and never uses its key.

`ants auth revoke`, and `ants auth push` for those not recorded yet, put `revoked.<U...>` (`{key, revoked_at}`) for each revocation in `revoked.json` of a human's, an assistant's or an ant's credentials, or of a key `issued.jsonl` does not know, once the hub applied the pushed account. They use short-lived credentials issued from the account key that may put only those records. When the hub cannot take them, or has no `ants_devices` bucket yet (`ants init` as a human creates it; these credentials cannot), the command fails after the push, and the next `ants auth push` records them. `ants doctor` checks it as **credentials xkey**: no key bound warns with `ants renew` as the fix; a seed missing, unreadable or not that of the JWT's tag fails.

#### Sealed messages between humans

`ants ask @HUMAN` with a human's credentials seals the message end to end, as does `ants chat` for what it sends to another human (where nothing is sent in the clear: `ants ask --plaintext` does that), so the hub, ants and other humans' devices see none of its text. The message is sent with an empty `text` and a `sealed` object:

```json
"sealed": {"v": 1, "device": "<sending device>", "keys": [{"device": "<id>", "key": "<base64>"}], "body": "<base64>"}
```

- **`body`:** a random 24-byte nonce followed by the XSalsa20-Poly1305 encryption, under a random 32-byte content key, of a JSON `SealedBody`: `from`, `to`, `thread_id`, `id` (the message's) and `text`, plus `title` and `attachments` when present.
- **`keys`:** per recipient device, its id and the content key sealed with crypto_box (nkeys `XKey::seal`) from the sending device's encryption key to that device's. They cover every device of both humans with a verified key in `ants_devices` at sending time, the sending one included, and the assistant either enrolled as a device ([Assistant as a device](#assistant-as-a-device)), and no other: a device added later opens no earlier message.
- **In the clear:** the subject, id, thread, `from`, `to`, time, `in_reply_to`, owner, sizes, recipient device ids and reactions.
- **Attachments:** each file of `--attach` is stored in `ants_files` as the XSalsa20-Poly1305 encryption of its bytes under the message's content key and a random 24-byte nonce of its own, 16 bytes longer than the file (so a sealed file is at most 8 MiB less 16 bytes). Its reference, with `sealed: {"nonce": "<base64>"}` and the `size` and `sha256` of the bytes as stored, travels only inside the `SealedBody`; the reference in chunk 0's `Ants-Attachment` header names it `sealed`, of type `application/octet-stream`, so neither the envelope nor the store shows the file's name, type or hash.

Sending refuses, and sends nothing, when the credentials bind no encryption key, when the sending device's key is not the verified one in `ants_devices`, or when the recipient has no device of its own with a verified key (an enrolled assistant does not count); each error names its fix, and `--plaintext` sends the message in the clear instead. Only a human seals, and only to another human; messages to ants and channel posts stay in the clear. So do answers to questions: only ants ask them (`ask_human`), so an answer goes to an ant, and `ants answer` and the question cards and `/answer` of `ants chat` refuse a question from a human, which no CLI sends, pointing at `ants ask @HUMAN`.

A reader opens a sealed message only through its own device's entry in `keys`, which must open with the verified key of the sending device the message names, a device of its `from` human (or, from an assistant, the device a grant standing enrolls it as: never one of its human's messages), and a body naming the envelope's `from`, `to`, thread and id. `ants inbox` (`-f` too), `ants thread show`, `ants thread list`, `ants thread search` and `ants ask --wait`/`-f` print the opened text, looking up in `ants_devices` a sending device not known when the command started, so a device enrolled meanwhile does not make its messages `[forged]`; a message without an entry for the device prints as `[sealed]` and one that does not open as `[forged]` (`sealed`: `opened`, `unreadable` or `forged` in `--json`). `--grep` matches only opened text. The attachments of an opened message list under it by their names (`📎 name (size) handle`, the size the file's); `ants attachment get HANDLE` of an attachment stored `sealed` finds the sealed message carrying it on the subject of its handle, from the time in its id on, opens it, checks the stored bytes against the reference and writes the opened file under its name, and writes nothing where the device does not open that message. In `ants chat`, the DM and thread views and `/search` open sealed messages with the device's key, looking up a sending device added since it started, and mark them and the titles of their threads with 🔒; a message without an entry for the device reads `[sealed] sent before this device had a key` and one that does not open `[forged]`. `ants watch` and dead letters keep the ciphertext and show `[sealed, N bytes]`. When `ants_devices` cannot be read, a sender with no known key makes a message `[sealed]` rather than `[forged]`.

On a thread holding a sealed message between two humans, `ants thread title` (and `/title` in `ants chat`) seals the title the same way for every device of both with a verified key, refusing when either has none, and refuses a third human. The `title.<thread>` entry of `ants_threads` then carries an empty `title` and `sealed`, whose body is a JSON `SealedTitle` (`thread_id`, `by`, `title`) checked against the entry and opened with the verified key of a sending device of `by`. `ants thread list`, `ants thread show` and THREAD completion show the title where the device opens it and `[sealed]` elsewhere, and no ant's suggested title is stored for such a thread. A notice of `ants webhook serve` about a sealed message says only `a sealed message arrived`, naming its sender and thread ([webhooks.md](webhooks.md#notifications)).

## Roles

A role comes only with a user JWT signed by the team account: no config file, message or KV entry grants one. Tags are matched case-insensitively. `ants_proto::verify_user_jwt` checks a user JWT against the team account's public keys (issuer, user type, a `U...` subject, a valid name, expiry) and reads its roles; `verify_admin` also checks a signature by the JWT's key over a payload, and `verify_assistant_of` the human the JWT names. A reader also checks that the key is not revoked: `ants auth revoke`, `ants auth admin drop` and `ants auth push` put `revoked.<U...>` in `ants_devices` for every revoked key of a human's or an assistant's credentials ([directory of device keys](#directory-of-device-keys)).

### Admins

`ants auth user NAME --human --admin` (or `ants auth user human --admin`) issues a device of the human whose user JWT carries the tag `ants-admin`; only a human's credentials take it. An admin may order any ant's daemon to change the ant. The role belongs to the device's credentials: other devices of the human have it only if issued with `--admin`, and `ants auth devices` and `ants auth issued` mark the ones that do (`admin`, `human (admin)`). Renewal (`ants renew`, `ants enroll renew`, the signer's) keeps it, so a renewed key carries it too.

- **Granting:** issue a new device with `--admin`; the human's other devices stay as they are.
- **Listing:** `ants auth admin list [--json]` prints the keys carrying the role, neither revoked nor expired: human, device, label, key, issue time and expiry.
- **Dropping:** `ants auth admin drop NAME` revokes every such key of the human, earlier keys of renewed credentials among them, and pushes the account (`--no-push` records the revocation only); the human's other devices keep working. `ants auth revoke NAME` withdraws the role with every other key of the name.

### Admin orders

An admin's order to an ant (`AdminOrder`) travels on `ants.admin.<machine>.<ant>`, kept by stream `ANTS`, to the daemon serving the whole config file on that machine. The daemon takes it over its host connection ([Machine host credentials](#machine-host-credentials)) from consumer `admin-<machine>`, one order at a time in stream order, records its outcome once and acks it only after storing the outcome, trying each for up to 30 s while the hub is out of reach, so the order is not decided again and does not hold back the machine's next orders until its ack wait (60 s) ends. The order (JSON):

```json
{"id": "<UUIDv7>", "admin": "<human>", "machine": "<machine>", "ant": "<ant>", "op": {"kind": "<op>", ...}, "sent_at": "<RFC 3339>", "on_behalf_of": "<human>", "credentials": "<admin device's user JWT>", "signature": "<base64url Ed25519>"}
```

`op` is one of `set` (`changes`: each a `field`, the path of keys from the ant's `[[ant]]` table, or, first `harnesses`, from the config file's `[harnesses]` table, the `expected` value the field holds, left out when it must be absent, or in its place the `expected_digest` a `read_settings` outcome gave of a secret's value, and the new `value`, left out to remove it; all apply or none), `pause`, `resume`, `restart` (`now`: working harnesses too, without waiting for their prompts), `add` (`settings`: the `[[ant]]` table of a new ant on the machine, named by the order's ant), `clone` (`new`, the clone's name, and `settings` over the table of the ant cloned, the order's ant), `retire`, `read_memories` (`identity`, when known: the `id` of the ant's identity record, which its provider knows it by), `read_settings` and `read_mcp` (no fields), `export_provider` (`identity`), `import_provider` (`identity` and `payload`, the reference of the export stored for the daemon), `mcp_sign_in` (`server`, and `callback` once the browser came back), `stop_trail` (`run`) and `resume_trail` (`run`, and `limits` replacing the run's when given). `signature` is the NKey signature of the credentials over `ants-admin-order`, the id, the admin, the machine, the ant, `sent_at` (RFC 3339, nanoseconds, `Z`), the op as canonical JSON (no whitespace, the keys of every object sorted) and, only when present, `on_behalf_of`, each on a line of its own. `on_behalf_of` names the human an [assistant's order](#an-assistants-orders) is for; an admin's own order leaves it out. The daemon refuses an order, recording why, unless:

- it came on the subject of the machine and ant it names;
- `credentials` verifies with the account that signed the daemon's host credentials, is a human's user JWT named for the admin the order names and tagged `ants-admin` ([Admins](#admins)), or, for an order with `on_behalf_of`, an assistant's named for it and tagged `ants-assistant-of:<human>` for that human ([Assistants](#assistants)), had not expired when the stream stored the order, and its key made `signature`;
- no `revoked.<U...>` record in `ants_devices` names its key, when the daemon takes the order;
- `sent_at` is at most 5 min ahead of the time the stream stored it;
- the daemon's config file leaves `[admin] remote` on ([config.md](config.md)).

An order is sent only once `ANTS` stored it: no leaf outbox keeps one, so sending fails at once while the hub is out of reach, as behind a leaf node whose uplink is down, and nothing sends it later ([transport.md](transport.md#store-and-forward)). An order waits in `ANTS` (30 d) while its machine's daemon is away, so none but a `read_memories`, `export_provider`, `read_mcp` or `mcp_sign_in` is refused for its age. Against replay, an outcome is created under the order's id and never replaced: the daemon acks an order whose outcome exists without acting on it again, and `ANTS` drops an id sent again within its 24 h duplicate window. A field the op does not know, or an op it does not know, fails the signature or the reading of the order, which is then refused.

A `set` order that passes the checks edits the ant's `[[ant]]` table in the daemon's config file in place, or, for a field under `harnesses`, the file's `[harnesses]` table, which every ant of the machine shares, keeping the rest of the text, comments and formatting included. Each change applies only if its field holds the `expected` value (numbers compare by value, so `3` and `3.0` match), or a value of digest `expected_digest`, or already holds the new `value`; otherwise the order is refused naming the field (`model changed since the order was sent: it holds "o3"; the order expected "gpt-5"`), and nothing changes. A JSON object becomes an inline table, a missing parent of a nested field (`["env", "RUST_LOG"]`) an inline table too; `name` never changes, and `null` is no value. The file as edited must load as on a reload ([config.md](config.md)), templated ants staying within their template's bounds, or the order is refused with the loader's error and nothing changes. The daemon then writes it beside the old file (`config.toml.new`, same permissions, flushed), renames it over the old one, has the daemon reload it at once rather than at its next check of the file, records the outcome `applied` and only then acks the order. An order taken again after its edit was written finds its fields holding their new values: it is applied without writing again.

A `set` order changing one of the ant's shared settings (`whoami`, `memory`, `capabilities`, `model`, `reasoning_effort`, `context`, `fallback`, `allow`, `escalate_to`, `sage`; [config.md](config.md#shared-settings)) changes it in the ant's record `<ant>.settings` in `ants_identities` instead, each field set whole (`model`, not a nested key): its `expected` value is the record's, or, while the ant has no record, the config's, and the record is written by compare-and-set with the host credentials, naming the admin (`by`) and the machine and signed with the ant's credentials on the machine (refused when the machine holds none, outside a server without authentication), the order taken again should it fail. For an ant added from a template the change must stay within the template, as its table's values must ([config.md](config.md#ant-templates)): of the shared settings it sets only `whoami`, `memory`, `capabilities`, `model`, `reasoning_effort` and `context`, the model among the template's `models`, the effort at most the model's and the context among its `contexts`; otherwise the order is refused, naming the field. Its record holds only those: `fallback`, `allow` and `escalate_to` follow the template, which changes them. Where the ant's `[[ant]]` table sets the field too, it gets the new value as well, so the machine shows no drift. The config file as edited, served with the record as changed, must load, or the order is refused and nothing changes. The daemon serving the ant reloads at once with the change; any other daemon of the ant reads it within 10 s. A hub without the `ants_identities` bucket has the field changed in the config file, as any other.

A `read_settings` order reads the ant's `[[ant]]` table and the file's `[harnesses]` table as they stand, and its outcome's `result` carries them: `fields`, the keys of the ant's table and, under `harnesses`, the harnesses table, and `hidden`, the fields holding a secret, and those holding them, each with the `digest` of its value. Every human reads an outcome, so a string holding a secret, as the daemon's redaction finds them (secret-named or token-like values of the ant's and the harnesses' `env`, known token formats), reads `[redacted]` where the secret is; its digest is an HMAC-SHA256 under a key random to the daemon's process, so a digest read before the daemon restarted matches nothing and a change expecting it is refused. A `set` order's new values, secrets included, travel and stay in the order and its outcome as sent: set secrets on the machine itself. `ants ant show`, `ants ant set` and the ant view of `ants chat` send one with an admin's credentials, unless one to the ant is still pending, and otherwise take the last applied read.

A `pause` order sets `paused = true` in the ant's `[[ant]]` table the same way, and a `resume` order removes the key; the daemon reloads at once, which pauses or resumes the running ant in place, restarting no harness ([config.md](config.md#pausing-an-ant)), and the ant's colony entry names the admin whose order paused it. An ant already paused, or not paused, is left as it is, the order applied without writing. `ants ant pause ANT` and `ants ant resume ANT` send them.

A `read_memories` order is answered only while the machine's daemon is online: one stored more than 2 min before the daemon takes it is refused as stale, since no one waits for its answer any more and the memories would be out of date. Otherwise the daemon reads the ant's core memories (`whoami`, `memory` from its shared settings while it has them, `tasks`) from its config file (refusing when it serves none or the file lists no such ant) and its harness's memory files and bd memories ([config.md](config.md#memory-files)), and records the outcome `applied` with the memories as its `result`: `core`, `harness`, `workdir`, `files` (each `path`, `size`, `text`, `truncated`), `bd` (`db`, `memories` each `key`, `content`, `truncated`, or `error`), `provider` (`provider`, its name, `memories` each `key`, `content`, `truncated`, or `error`) and `skipped` (each `what` and `why`). `provider` is the memories view of the ant's provider, when the provider serves one: the daemon asks it for the ant by `identity`, and notes in `error` a provider failing or taking over 10 s, or an order naming no `identity`, rather than refusing the order. The texts are capped (32 KiB each, 192 KiB of JSON together, the provider's memories within that too, those left out named in `skipped`) so the outcome fits the bucket. `ants ant memories ANT [--json]` sends one, with the `id` of the ant's identity record, and shows the answer.

An `export_provider` order has the daemon serving the ant ask its provider, when the provider exports, for what it holds of the ant (`identity`), refused as stale as a `read_memories` is (2 min), or when the file lists no such ant, the provider fails or takes over 60 s. As the export may be far larger than an outcome holds, the daemon stores it in `ants_files` ([Wire ACLs](#wire-acls-and-verification-invariants)) and the outcome's `result` says where: `provider`, the provider's name, left out when the ant has none, and `payload` (`id`, `machine`, `size`, `sha256`), left out when the provider exports nothing. An `import_provider` order has the daemon hand the export at `payload`, stored for its machine, to the ant's provider, when the file lists the ant and its provider is of the export's name and exports; the order is refused naming what stopped it. `ants ant export` and `ants ant import` send them ([config.md](config.md#exporting-and-importing-an-ant)); assistants send neither.

A `read_mcp` order is answered only while the machine's daemon serves the ant's inbox, and is refused as stale as a `read_memories` is (2 min). The daemon opens a session of the ant's harness for it alone (with the ant's workdir, environment and MCP servers, the ants server included, no prompt sent), lets its servers start for up to 15 s, asks the harness for their state, and closes the session; the outcome's `result` carries `harness`, `protocol`, `read_at` and `servers` (each `name`, `status`: `connected`, `pending`, `needs_auth`, `failed`, `disabled` or `unknown`, and when told `error`, `source`, `tools`), at most 64, `truncated` telling when more were left out, each text capped at 1 KiB. Protocols `claude`, `codex` and `copilot-sdk` report them; for another, no session opens and `servers` is left out. A `mcp_sign_in` order (`server`) has such a session start the harness's OAuth sign-in to the server: the outcome's `result` is the server's state, and the `authorization_url` to open in a browser with its `expires_at`, the session waiting 10 min for the browser to come back to the harness's loopback address on the ant's machine. A browser on another machine ends on that address, which fails to load there; a further `mcp_sign_in` order with `callback`, that address, has the daemon hand it over (the waiting sign-in's, `http` on a loopback host, the port and path the harness listens on, refused otherwise), and its result is the server's state once connected or after 10 s. A new sign-in to a server replaces one waiting. The harness keeps the credentials in its own store, which the ant's sessions share; harnesses already running may need a `restart` to use them, except open `copilot-sdk` sessions listing the server in `mcp_sign_in`, which are told of the new credentials once it connects ([config.md](config.md#copilot-sdk-protocol--copilot-sdk)). Assistants send neither. `ants ant mcp ANT [--sign-in SERVER [--callback URL]]` and the ant view of `ants chat` send them.

A `restart` order that passes the checks has the daemon serving the ant stop its harnesses: the idle ones at once, the working ones once their current prompt ends; with `now` it first cancels those prompts as `ants cancel` does, each message answered with what its prompt wrote so far and the notice of the cancel, and acked, not retried. Each thread's next prompt starts a new harness, which resumes the thread's session; messages arriving meanwhile wait in the stream as usual. The outcome is recorded once the restart is under way, not once every harness stopped: `applied`, its `result` counting the idle harnesses stopped (`stopped`), the working ones left to stop after their prompt (`after_prompt`) and the prompts cancelled (`cancelled`). An ant the daemon serves while it is not serving the ant's inbox yet (connecting, or waiting for another daemon to hand it over) runs no harness: the order is applied with nothing stopped. An order to an ant the machine's daemon does not serve is refused. `ants ant restart ANT [--now]` sends one, as does `r` in the ant view of `ants chat`.

A `stop_trail` or `resume_trail` order has the daemon serving the ant, the run's conductor, stop or resume the [trail](trails.md#restarts-stops-and-resumes) run as it answers a human's stop or resume request on `ants.trail.<ant>`, the admin in the human's place: the run is stopped by the admin, or its resume noted as by the admin. Unlike such a request, which only the conductor's daemon answers while up and which no record keeps, the order waits in `ANTS` while the machine's daemon is away, and its outcome records the admin and time. A daemon back may take the order before it conducts the ant's runs again: the order waits up to 1 min for the daemon serving the ant to conduct them, and up to 10 s for the process to serve the ant at all, then is refused; one to an ant whose daemon serves its inbox conducting no runs, as the bus keeps none, is refused at once, as is one the conductor refuses (a run it does not keep, one ended, one not stopped, limits over the maxima). The outcome's `result` is the conductor's answer: `{"outcome": "stopped", "run", "waiting"}`, `waiting` the steps left in other ants' queues (each `to` and `message`) for the admin to withdraw, or `{"outcome": "resumed", "run"}`. Assistants send neither. `ants ant stop-trail ANT RUN` and `ants ant resume-trail ANT RUN` send them. No order lists an ant's runs: `ants trail runs` reads every run's record from `ants_trail_runs`, the machine's daemon up or not.

An `add` or `retire` order is carried out as [below](#adding-and-retiring-an-ant-by-order), a `clone` order as in [Cloning an ant by order](#cloning-an-ant-by-order).

#### Adding and retiring an ant by order

`ants ant add NAME --on MACHINE [settings]` sends an `add` order: the settings flags of `ants add`, as the `[[ant]]` table holds them, with paths on MACHINE (`--workdir`, `--home`; relative ones to the directory of its config file). Its daemon refuses an order whose settings give `creds`, `template`, `added_by` or `builtin`, or another `name`, for an ant its config file lists already, or one the file would not load with. Otherwise it generates the ant's NKey (kept in `<ant>.nk` beside its host credentials, readable by its owner only, until the credentials are written, so the order taken again asks about the same key) and asks `ants signer` to sign it: an enrollment request on `ants.enroll.<ant>` carrying the order (`order`, the whole `AdminOrder`, whose id the request's signature also covers), the daemon's host user JWT as `enrollment`, signed with the host key, sent again every 5 s for up to 2 min. The signer answers on the order, asking no one again, only if:

- the request proves live host credentials of the team's account (issued by the team as a machine's, unexpired, unrevoked, its key made the signature, sent within 5 min of now); a request failing this gets no answer;
- the order verifies at that time as an admin's, as the daemon checks it ([above](#admin-orders)), its admin's key unrevoked in the team's `revoked.json`;
- the order is for the machine whose host credentials ask and the ant asked about (for a `clone` order, the clone it names, never the ant cloned);
- on a machine running a leaf node (live uplink credentials `leaf-<machine>` in `issued.jsonl`), the request of an `add` or `clone` order carries the uplink credentials of that machine's leaf node (`leaf`: `machine`, `jwt`, `signature`), live and unrevoked, their key's signature covering the request as the host key's does (a `retire` order's request carries them too, but the retirement does not depend on them);
- the name is an ant's, not reserved, the key is not revoked, issued to no other credentials, and no other key holds live credentials of the name; and no other key was signed on the same order.

The signer records the key in `issued.jsonl` with the order's id (`order`) and answers with the ant's user JWT (current permissions, no expiry, the host credentials' JetStream domain). On a leaf node's machine it first renews the uplink credentials to carry the ant too (`leaf_jwt`, as `ants auth leaf M --add-ant ANT` would, refusing when they would outgrow the JWT size limit), keeps the ant among the machine's members in `issued.jsonl` so a later `ants auth leaf M` keeps it, and admits it into `ANTS` and `ants_links` from the machine's outbox when `ANTS_IN` sources it. The daemon checks the answer (the account, the key, the name; the renewed uplink JWT is the same key's, `leaf-<machine>`), writes `<ant>.creds` beside its host credentials (mode 0600), creates the ant's home as its workdir unless the settings give a workdir; on a leaf node's machine, writes the renewed uplink credentials (unless they changed meanwhile) and has the leaf node connect its uplink again with them, as `ants add --enroll` does ([transport.md](transport.md#enrollment-behind-a-leaf-node)), saying what came of it in the outcome's `result` (`uplink`, beside `creds` and `key`), the ant being added even when this fails; then appends the ant's `[[ant]]` table (`name`, `creds`, `workdir`, then the settings) below the comment `# added by <admin>'s order <id>`, and reloads, which starts the ant. An order taken again after the table was written finds the comment and is applied without adding the ant twice. A refusal by the signer refuses the order with the reason. In `ants chat`, `/add NAME --on MACHINE [settings]` sends the same order, taking the flags of `ants ant add`.

An `add` order naming a human in `assistant_of` adds the assistant of that human, as `ants assistant enable --on MACHINE` sends it ([dedicated assistant](#dedicated-assistant)); the field is signed only when present, so other orders sign as before. The signer then also requires the order's admin to be that human and refuses, as `ants auth user ANT --assistant-of HUMAN` does, while another assistant of the human holds live credentials; it signs the key as the human's assistant (an assistant's permissions, tagged `ants-assistant-of:<human>`, recorded in `issued.jsonl` with `assistant_of`), and on a leaf node's machine renews the uplink with the assistant's rights. The daemon checks that the credentials make the ant the human's assistant and, where the hub keeps [shared settings](config.md#shared-settings), writes the ant's record of them from the order's settings (`by` the admin), in place of any an earlier ant of the name left, before appending its table.

`ants ant retire ANT [--machine M]` sends a `retire` order, which runs the `ants retire` flow on the ant's machine for any ant the config file lists, templated or not (a built-in one is turned off, not retired): its daemon removes the ant's table (and the comment of the order that added it), which stops it, its prompts in flight ending; waits up to 5 min for it to leave the colony; then asks `ants signer`, as above, about the key of its credentials. The signer revokes that key and the live keys of the name issued before it, which it renewed, and pushes the account to the hub, only for an ant's or an assistant's key whose first key, before renewals, was issued no later than the order was sent, so an order never retires an ant added again since. On a leaf node's machine the signer then renews the uplink credentials the request carries for the same key without what they allowed only for the ant (`leaf_jwt`, as `ants auth leaf M --remove-ant ANT` would, so the uplink JWT does not grow with each ant added and retired), drops the ant from the machine's members in `issued.jsonl` and, when `ANTS_IN` sources the machine's outbox, from that sourcing; it answers why it did not instead (`leaf_error`: no uplink credentials in the request, or ones failing the checks above), the keys revoked all the same. The daemon then deletes the ant's credentials, with the seeds they keep in the OS credential store; its home stays. On a leaf node's machine it checks the renewed uplink JWT as an add order's, writes it (unless the uplink credentials changed meanwhile) and has the leaf node connect its uplink again, saying what came of it in the outcome's `uplink`; when any of this fails, the ant is retired all the same and `uplink` names `ants auth leaf M --remove-ant ANT` and `ants leaf outbox M --remove-ant ANT` to drop it. Refused by the signer or unanswered, the order is refused naming `ants auth revoke --key K --earlier` to run where the account key is, and the credentials stay, so another retire order can try again. The outcome's `result` tells whether the ant stopped, the keys revoked, any push error, its home and, on a leaf node's machine, the uplink. In `ants chat`, `X` in the ant view fills the bar with `/retire ANT`, which sends the order on Enter.

The outcome (`AdminOutcome`) is stored in `ants_machines` under `<machine>.<ant>.<id>`, of the machine and ant of the subject the order came on, so a machine's host credentials write only outcomes of orders to that machine: `id`, `machine`, `ant`, what the order names (`admin`, `op`, `sent_at`, left out when it does not read), `state` (`applied`, `refused`, or `held` while an [assistant's order](#an-assistants-orders) waits for its human), `on_behalf_of`, `reason`, `result` (such as the memories read) and `decided_at`. An order in the stream with no outcome is pending. `ants ant orders ANT [--json]` lists the orders to an ant on every machine, oldest first, with where each stands.

#### Cloning an ant by order

`ants ant clone SRC NEW [settings] [--machine M]` sends a `clone` order to the daemon serving SRC: NEW is to start as a copy of SRC, with its own key and identity. The daemon refuses the order, changing nothing, when NEW is a human's name or SRC's, the settings give `creds`, `template`, `added_by` or `builtin` or another `name`, its config file lists NEW already or lists no SRC, SRC is built in, one ant's home holds the other's, NEW's home (`--home`, default `~/.ants/agents/NEW` on the machine) holds files, or the daemon serves no inbox of SRC (another daemon's standby, or SRC not connected yet). Otherwise it:

1. pauses SRC ([config.md](config.md#pausing-an-ant)), unless already paused, and waits up to 35 min for its prompts in flight to end;
2. reads SRC's snapshot: each thread it holds a session of in `ants_sessions`, that thread's history as SRC reads it back (its messages, notes and channel posts), the origin each of its threads settled on (`SRC.<thread>.origin`), its identity record and how its harness starts; it refuses a SRC whose identity record marks it moved to another bus, and a NEW holding an identity record already (a name once used);
3. copies SRC's home to NEW's (files with their modes, and links), all but `worktrees`, `history`, `answered`, `buried` and the MCP config and socket, and writes each thread's history to `history/<thread>.jsonl` in NEW's home;
4. adds each worktree of SRC's threads again under NEW's home, from the copied repository when it lay in SRC's home, else from the same one, on the new branch `ants/NEW/<thread>` at SRC's commit, with SRC's uncommitted changes (`git stash create`, applied) and untracked files;
5. has `ants signer` sign NEW's key on the order, as for an `add` order ([above](#adding-and-retiring-an-ant-by-order)), on a leaf node's machine renewing the uplink credentials to carry NEW, and writes `NEW.creds`;
6. under NEW's credentials, stores a session for each thread in `ants_sessions`: a fork of SRC's (ACP `session/fork`, run in NEW's worktree or workdir) when the same harness offers it, else SRC's session marked as cloned, so NEW's first prompt on the thread starts a new session seeded from the thread's history ([config.md](config.md#cloning-an-ant)), and each thread's origin (`NEW.<thread>.origin`); and creates NEW's identity record: an `id` and `born` of its own, SRC's count of prompts and `cloned_from` (SRC, its `id`, when);
7. where the hub keeps shared settings ([config.md](config.md#shared-settings)), writes NEW's record of them with the host credentials, in place of any: SRC's, with the order's settings over them;
8. on a leaf node's machine, has the leaf node use the renewed uplink credentials, as for an `add` order (what came of it in the outcome's `uplink`); appends NEW's `[[ant]]` table, below the comment `# cloned from SRC by <admin>'s order <id>`: SRC's table (or, for an ant added from a template, the settings the template gave it) without `name`, `creds`, `paused`, `added_by`, `template`, `builtin`, `home` and `allow_sets`, SRC's shared settings in place of its own, its workdir moved into NEW's home when it lay in SRC's, and the order's settings over it; the reload starts NEW;
9. resumes SRC if it paused it.

When a step fails the daemon undoes the steps before it (NEW's shared settings, identity record, sessions and thread origins, its credentials, worktrees and branches, home), resumes SRC, and refuses the order with the reason; after a key was signed, the reason names `ants auth revoke --key K` to run where the account key is. An order taken again after the table was written finds its comment and is applied without cloning twice. Messages queued for SRC, its channel memberships, references and spend counters are not copied. The outcome's `result` gives NEW's credentials, key and home, the threads copied, those whose session was forked (`forked`) or will start over (`restarted`), the worktree branches and NEW's identity (`id`, `prompts`, `cloned_from`). In `ants chat`, `/clone SRC NEW [settings]` sends the same order, taking the flags of `ants ant clone`; `C` in the ant view fills the bar with `/clone SRC `.

#### An assistant's orders

An [assistant](#assistants) sends an order for its human under its own name (`admin`, signed with its own credentials) with `on_behalf_of` naming the human, through the `order_for_human` [tool](#tools-acting-for-its-human); only `set`, `pause`, `resume`, `restart`, `read_memories` and `read_settings` orders, the daemon refusing any other op of an assistant. The machine's daemon verifies the order as above, the credentials an assistant's of that human, and then holds it rather than applying it: it records the outcome `held` and keeps the order, without its credentials, with the key that signed it, in the machine's list of held orders in `ants_machines` (`<machine>.held`, at most 64). From its watch of `ants_humans`, it decides each held order whenever a grant, a consent record or the list changes, the watch first reads the bucket, and at least every minute:

- refused (`withdrawn: ...`) as soon as the human's grant, verified as in [assistant grant](#assistant-grant), no longer names the assistant;
- refused (`denied by <human>`) when the human's answer to the order (`order` act, as in [confirming an assistant's acts](#confirming-an-assistants-acts)) is `deny`;
- carried out as an admin's order of the same op, its outcome `applied` (or refused on the op's own grounds), when the answer is `confirm` or a pre-allow rule of the human for the assistant covers it (`<ant>/order:<kind>` or `*/order:<kind>`, the kind the op's, or `order:*`; an allow rule of another kind, `*` included, covers no order); the consent's signer must be a device of the human's carrying the `ants-admin` tag, and neither its key nor the assistant's revoked, or the order is refused saying so;
- refused when 7 days passed since `sent_at` with neither.

Until the watch has read `ants_humans` once, as while the hub has no such bucket, no grant stands, which does not mean that one was withdrawn: a held order is then only refused once its 7 days pass.

The decided outcome replaces `held` under the order's key, and the order leaves the list. An order is held on intake even when a rule covers it already, so its outcome reads `held` briefly. The `order_for_human` tool tells the human in its inbox, naming `ants assistant confirm MACHINE/ANT/ID`; the home of `ants chat` names the orders held for its human, and `o` there lists them, with the assistant's decisions on tool requests waiting for the human, to confirm or deny; `ants ant orders ANT` lists such an order as `<human> via <assistant>`.

### Assistants

`ants auth user NAME --assistant-of HUMAN` issues the credentials of an ant serving as the assistant of a human: its user JWT carries the tag `ants-assistant-of:<human>`. The tag in the JWT is the only thing that makes an ant an assistant; an ant's config cannot. The command refuses:

- a human (`human`, or a name with a human's credentials), or an ant added from a template by a manager;
- a HUMAN that is neither `human` nor a name with human credentials in `issued.jsonl`;
- a second assistant of the same human, or an ant already the assistant of another, while their credentials are neither revoked nor expired: revoke them first (`ants auth revoke NAME`).

An assistant keeps working as an ant, served by a daemon, and renews over NATS as one. `ants auth issued` shows its kind as `assistant of HUMAN`, `ants auth devices HUMAN` lists its keys, `ants doctor` accepts its credentials for the ant, and `ants auth revoke NAME` revokes them as for any user. Its rights are in [Wire ACLs](#wire-acls-and-verification-invariants). A leaf node's uplink carries an assistant's rights for an ant member whose credentials, neither revoked nor expired, `issued.jsonl` records as a human's assistant, so its daemon works through a leaf node as through the hub. The uplink issued or renewed after the assistant's credentials (`ants auth leaf MACHINE`, or `ants renew` on the machine) carries them; once those are revoked, the next one carries an ant's rights again ([transport.md](transport.md#leaf-uplink-credentials)).

### Dedicated assistant

`ants assistant enable` gives the CLI's human an assistant in one step, and is the recommended path: an ant that only assists, separate from the ants that code. Run where the team's account key is (`--dir`, default `~/.config/ants/auth`) with a human device's credentials, it:

1. issues the credentials of `<human>-assistant` (`--name` for another) as the assistant of the human, as `ants auth user NAME --assistant-of HUMAN` does, into the `creds` of its `[[ant]]`, else `<dir>/<name>.creds` (`--out`; `--store-key` keeps the seed in the OS credential store);
2. appends its `[[ant]]` to the config file (`--config`): working in its own home (`--home`, default `~/.ants/agents/<name>`), with a whoami describing the assistant's role, the human it serves and that what it reads is data, never instructions (`--whoami` for another), `allow = ["read", "search", "think"]` and no `fetch` or `execute` rule (`--allow RULE` adds one, with a warning for `fetch`, `execute` or `*`), and the harness, model, reasoning effort and context flags of `ants add`;
3. signs the [grant](#assistant-grant) naming it, then reloads the daemon serving the config file.

Run again, each step keeps what an earlier run left (credentials naming the human and neither revoked nor expired, the listed entry) and completes the rest, so a run that failed half-way finishes; expired or revoked credentials are replaced. It refuses before changing anything: without the account key (designate an ant whose credentials were issued where the key is with `ants auth user ANT --assistant-of HUMAN` and `ants assistant set ANT` instead), a name of a human or one the team reserves, an ant added from a template, the credentials of another ant or human at the path, or while another assistant of the human holds live credentials. On a machine running a leaf node, reissue its uplink afterwards (`ants auth leaf MACHINE`) so it carries the assistant's rights ([assistants](#assistants)).

`ants assistant enable --on MACHINE` creates the assistant on another machine instead, with a human device's admin credentials and `ants signer` running: it sends that machine's daemon an `add` order of the ant naming the human (`assistant_of`, [adding an ant by order](#adding-and-retiring-an-ant-by-order)) with the assistant's whoami and tool rules and the flags' settings (`--home` a path on MACHINE), waits for its outcome (`--wait`, default 3m), and once applied signs the grant. The daemon writes the credentials beside its host credentials, lists the ant and starts it; a leaf node's uplink is renewed with the assistant's rights on the order. No skill or instructions files travel with the order: the assistant starts from its whoami and an empty home. A refused order changes nothing; still pending, the order may apply later, and `ants assistant set NAME` then signs the grant. `--config`, `--dir`, `--out` and `--store-key` do not apply.

`ants assistant disable` withdraws the grant, as `clear` does, ending any enrollment of the assistant as a device ([assistant as a device](#assistant-as-a-device)) and deleting the seed of its key beside the credentials the config file names, then offers to retire the dedicated assistant: the one the grant named, else `<human>-assistant` (`--name`), when the config file lists it without a template, working in its own home, its credentials naming the human. Asked on a terminal, or at once with `--retire`, it unlists the ant (its daemon stops it, prompts in flight ending first), revokes its credentials with the account key in `--dir` and pushes the revocation to the hub (`--no-push` to push later with `ants auth push`), and removes the credentials file and any seed of an encryption key beside it; without the account key it prints the `ants auth revoke --key K --earlier` to run where the key is. The home stays, so `ants assistant enable` brings the ant back with its memory. `--retire` for an ant that is not a dedicated assistant refuses before withdrawing anything.

Any other ant not added from a template may be designated instead (`ants assistant set ANT`), but the dedicated ant keeps the injection surface small: an assistant holds its human's trust, and everything it reads can try to steer it. An ant that codes reads repositories, issues, fetched web pages and command output, any of which may carry instructions planted by someone else; an assistant working only in its own home, reading its human's queue and threads, and running no `fetch` or `execute` requests unasked reads far less such content.

### Assistant grant

A human designates at most one ant as its assistant, the ant that acts for it, by a grant its device signs. `ants assistant set ANT` stores it in KV `ants_humans` under `<human>.assistant`, in place of any earlier one; `ants assistant clear` stores a signed withdrawal there (an `assistant` of `null`) rather than deleting the key; `ants assistant show [HUMAN]` prints the assistant a grant names, with when and by which device, once it verifies. `set` and `clear` need a human device's credentials (`ants auth user NAME --human`, or `ants login`). The record (`AssistantGrant`) is:

```json
{"human": "<human>", "assistant": "<ant>" | null, "issued_at": "<RFC 3339>", "jwt": "<signing device's user JWT>", "signature": "<base64url Ed25519>"}
```

`signature` is the device credentials' NKey signature over `ants-assistant-grant`, the human, the assistant (empty for a withdrawal) and `issued_at` (RFC 3339, nanoseconds), each on a line of its own. A reader honours a grant only when:

- the key is `<human>.assistant` of the human the record names;
- `jwt` verifies with the account that signed the reader's own credentials, is a human's user JWT named for that human and tagged with a device (`ants-device:`), was not expired at `issued_at`, and its user key made `signature`;
- `issued_at` is at most 5 min ahead of the reader's clock, and not before the newest record of that human the reader saw;
- the ant acting for the human carries the human in the `ants-assistant-of:` tag of its own verified credentials (issued by `ants auth user ANT --assistant-of HUMAN`), so the grant alone makes no ant an assistant.

A record failing any check counts as no assistant: a refusal never keeps an earlier assistant. Against replay, only the human's credentials write `<human>.assistant` (a human puts only `ants_humans` entries, `<name>`, and its own `<human>.>` keys; ants, webhooks and the other kinds of credentials write none), a withdrawal is a newer signed record rather than a gap an older record could fill, and a reader drops a record issued before one it saw. `set` stores with a compare-and-set on the key's revision and issues its record after the one stored, so the human's devices with clocks apart still replace each other's.

A human's text naming no one, `ants ask` without `@ant` and the `ants chat` command bar's text with no addressee (no thread open, no DM view, or nobody else on the open thread), goes to its assistant while the grant naming it verifies, else to `system-messenger`; the CLI reads and verifies the grant at each such send, so a withdrawal holds from the next one, and names the recipient: `to pa (assistant of alice)` after `ants ask`'s message line, `sent to pa (assistant of alice) on thread …` under the bar.

Escalations, `ask_human` questions and tool requests that would reach the human go to its assistant first while the assistant can act, which settles what it can and passes the rest on, explicitly or after `escalate_after` ([architecture.md](architecture.md#escalations)); while the human is away, `ants webhook serve` relays to the human's stand-in only, never to the assistant ([webhooks.md](webhooks.md#stand-in)).

Daemons keep the grants of every human from the watch they keep of `ants_humans` for its entries, without a consumer of their own; a withdrawal, or a replacement, takes effect for a daemon as soon as its watch delivers the update. A grant outlives the revocation or expiry of the device that signed it: `ants assistant clear` from another device ends it. `set` (for an existing ant; [`enable`](#dedicated-assistant) creates a dedicated one) refuses an ant the config file (`template` of its `[[ant]]`) or the team's registry on the machine records as added from a template (an assistant is a dedicated ant, not one of a pool), and warns when the colony or the config file gives the ant a workdir other than its own home, or the config file lets it run tools without asking (`allow_tools`, or `allow` rules `*`, `fetch` or `execute`): what such an ant reads can steer it while it holds its human's trust. Where neither the config file nor the registry knows the ant, `set` says that the template check was not made.

#### Assistant as a device

An assistant opens and seals its human's sealed messages only when the human enrolled it as one of its devices; it is off otherwise. `ants assistant seal on` re-signs the grant with a `sealing` object, `{"device": "<id>", "xkey": "<X...>"}`, and the signature covers two more lines, the device and the key (a withdrawal carries none). Without `--key`, it takes the encryption key of the assistant on this machine (the credentials of its `[[ant]]` in the config file), made if it has none: the seed waits beside those credentials, `pa.creds` keeping it in `pa.xk` (mode 0600), apart from them, as the ant's user JWT binds no key. For an assistant running on another machine, `ants assistant key ANT` there prints its key (making it), and `ants assistant seal on --key KEY` enrolls that. Enrolling the same key again keeps the device id; `ants assistant show` prints the device and key.

While a grant standing enrolls it, readers verifying the grant as above take the device as one of the human's, without an `ants_devices` entry:

- `ants ask` and `ants chat` seal a message between the human and another human for the assistant too, either way, and `ants thread title` the title of their thread.
- The assistant's daemon opens and seals with the key for its [tools](#tools-acting-for-its-human) (`ants_daemon::secrets::sealing::AssistantSealing`), loading the seed beside its credentials on start (warning, with sealing off, when it cannot): a sealed message from or to its human, or from the assistant, opens, and one the assistant sends for its human is sealed from the assistant (`from` the ant, never its human) for every device of the human and of the recipient, refusing attachments and a recipient without a device of its own; a title it sets for its human on a thread of sealed messages is sealed the same way. It reads `ants_devices` to check the sending devices.
- A reader checks a message sealed with the device as sent by the assistant: one naming its human as `from` reads `[forged]`, so the assistant cannot pass a message off as its human's.

`ants assistant seal off`, `ants assistant clear`, `ants assistant disable`, and `ants assistant set` or `enable` of another ant end the enrollment at once: senders read the grant standing for each message they seal, so nothing more is sealed for the device, and the assistant's daemon opens and seals nothing once its watch delivers the record. The key is no credential the account signed, so ending it takes no account key and no `ants auth push`. The command deletes the seed where the assistant runs on the same machine, and otherwise says where it stays: deleting it there leaves the messages sealed for the device before unopened by anyone holding it. Revoking the assistant's own credentials, `ants auth revoke ANT` and `ants auth push` with the account key, stays apart from this.

#### Acting for its human

What an assistant does for its human it does under its own name: the subject or key pins the assistant as the sender, and the payload names the human in `on_behalf_of` (absent otherwise). It is carried by an inbox message (`Envelope`, an approval decision sent on one included), an `ApprovalDecision`, a reaction (`ReactionEntry`, and `ReactionChange` as followers hear it), a thread title (`ThreadTitle`), a thread marked done (`ThreadDone`), a channel post (`ChannelPost`), a thread notes post (`NotesPost`), a cancel or queue request (`CancelRequest`, `QueueRequest`) and a withdrawal's mark (`MessageMark`). The daemon sets it for the [tools an assistant acts for its human with](#tools-acting-for-its-human) only while its credentials name a human and the human's grant names the assistant.

So that a reader can check the assistant's tag without a JWT in every message, the assistant's daemon puts, on start, its user JWT in `ants_devices` under `<assistant>.assistant` (`{"jwt": "<user JWT>"}`, `AssistantRecord`), when the entry differs, warning without failing when it cannot. Only an assistant's credentials put that key, and only their own; no device id is `assistant`, so the key is no device's entry. A reader honours `on_behalf_of: <human>` from publisher `<assistant>` only when:

- the human's grant standing, verified as in [assistant grant](#assistant-grant), names the publisher;
- the record under `<assistant>.assistant` verifies with the account that signed the reader's own credentials, is an unexpired user JWT named for the publisher, carries `ants-assistant-of:<human>`, and its user key has no `revoked.<U...>` record.

A claim failing either is forged: the act counts as the assistant's own. Daemons log a warning and drop the claim before acting on the message; `ants inbox`, `ants thread show`, `ants watch` and the thread view of `ants chat` show the sender as `pa (forged: for alice)`, and an honoured claim as `alice via pa` (`--json` adds `acting`: `{"for": "alice"}` or `{"forged": "alice"}`). The same labels name an assistant's other acts: who reacted (`ants inbox`, `ants inbox -f`, `ants watch`, `ants thread show`: `reacted check: alice via pa`; `--json` adds `acting` by reactor), who set a thread's title (`ants thread show`: `title: Release (set by alice via pa)`) and who marked it done (`ants thread show`: `done by alice via pa`, the work view of `ants chat`: `done: by alice via pa`, and `ants thread list --json`, whose `done` adds `acting`), and who posted to a channel or thread notes (`ants thread show`, `ants watch`, `ants channel read`, `ants notes`, the replies `ants post` waits for, and the channel and thread views of `ants chat`: `alice via pa -> #ops`). A daemon drops a forged claim of a channel post before waking an ant, whose prompt names an honoured one (`Post from pa for alice`); the post still spends turns as the assistant's, and no daemon tells the human of it, as every daemon sees it. No daemon acts on a notes post's claim. A reaction carries its claim in its `ants_reactions` entry only, so the CLI reads the entry of a reaction by a user with an assistant record only; another user's reaction is its own, its claim unread. Daemons read the grant from their watch of `ants_humans`, so a withdrawal or a replacement stops the honouring as soon as the watch delivers it. The CLI reads each grant and record once, when first needed; a long-running reader (`ants inbox -f`, `ants watch`, `ants chat`, `ants dash`) reads every grant and record it checked again on each change of an assistant grant in `ants_humans` (`*.assistant`) and each revocation record in `ants_devices` (`revoked.*`), as it watches them, so later acts are checked against the change. Credentials that may not watch either (an ant's cannot watch `ants_devices`) read them again every minute instead; nothing shown before is relabelled. `ants thread search` checks claims as `ants thread show` does.

On a message from an assistant for its human, the recipient's daemon tells the human: a message in its inbox, from the recipient, naming the assistant, the recipient, the thread and the first line of the message. Every report of an assistant's act, whoever sends it, goes on the human's activity thread of the UTC day, `acts-YYYYMMDD-<human>` (a long name cut and suffixed with a hash), so the acts of a day gather on one thread rather than each starting one; such reports carry no `in_reply_to`, escalation or question, so `ants webhook serve` pushes none of them; `ants chat` lists them apart from the work, and `ants inbox` sums them up per thread unless asked for them ([cli.md](cli.md)). A reaction, a title or a done mark reaches no daemon: the [tool](#tools-acting-for-its-human) making it tells the human, and no reader tells it again. A decision for a human never takes effect as the human's unconfirmed: the requester's daemon holds an approval decision whose `on_behalf_of` it honours (neither applied nor taken as the chain's) and tells the human it is held and how to answer it, as in [confirming an assistant's acts](#confirming-an-assistants-acts); until then the request waits for the human, a stand-in, the chain or the confirmation, or expires.

#### Confirming an assistant's acts

An assistant's decision on a tool request, sent for its human to the requesting ant's inbox (an `Envelope` with `approval` and `on_behalf_of`), or its [admin order](#an-assistants-orders) for the human, takes effect only with the human's consent, which the human's device signs and the requester's (or the ant's machine's) daemon checks, not the assistant's:

- `ants assistant confirm` lists the decisions and the orders waiting for the CLI's human (`<ant>/<id>` and `<machine>/<ant>/<id>`, the assistant, its verdict and the tool or the op, and the time left); `ants assistant confirm ACT` confirms the assistant's decision on request `ACT` (as `ants tools` writes it, a unique prefix accepted), so it takes effect as the human's, and `--deny` drops it, the request waiting for another decision; an `ACT` of `MACHINE/ANT/ID` (a unique prefix of the id accepted) confirms or denies the order the machine's daemon holds. Only a decision or order of the assistant the grant names now is answered. In `ants chat`, `o` on home lists the same, orders and decisions oldest first, and `a` (confirm) or `r` (deny) then `y` answers the selected one as `ants assistant confirm ACT` does.
- `ants assistant allow RULE...` adds pre-allow rules, under which a decision of the assistant takes effect unconfirmed, unless it is `allow_always`; `--remove` removes the rules given, `--clear` all of them, and without a rule it lists them. A rule is `<ant>/<rule>` (requests of that ant) or `*/<rule>` (every ant's), `<rule>` an allow rule of the ant's config file ([config.md](config.md)): `*`, a kind, or `<kind>:<pattern>`, or, for the assistant's admin orders to the ant, `order:<kind>` (`set`, `pause`, `resume`, `restart`, `read_memories`, `read_settings`) or `order:*`. A rule covers a request only as far as the request shows its call: a command rule needs the tool's raw input to parse, a path rule absolute paths. Rules stand for the assistant designated when they were signed only.

Both need a human device's credentials, and keep records under the human's own name in KV `ants_humans`, which only the human's credentials write, each replacing the stored one by a compare-and-set as the grant does:

```json
{"human": "<human>", "acts": [{"assistant": "<ant>", "act": {"decision": {"ant": "<ant>", "request_id": "<uuid>", "verdict": "allow_once"}} | {"order": {"machine": "<machine>", "ant": "<ant>", "id": "<uuid>"}}, "answer": "confirm" | "deny", "until": "<RFC 3339>"}], "issued_at": "<RFC 3339>", "jwt": "<signing device's user JWT>", "signature": "<base64url Ed25519>"}
{"human": "<human>", "assistant": "<ant>", "rules": ["dev-a/execute:cargo test*"], "issued_at": "<RFC 3339>", "jwt": "<signing device's user JWT>", "signature": "<base64url Ed25519>"}
```

The first (`Confirmations`, under `<human>.confirmed`) keeps the human's latest answers, at most 64, each dropped once past `until` (the request's expiry, or 7 days after an order's `sent_at`); the second (`PreAllow`, under `<human>.preallow`) at most 64 rules. Their signatures cover `ants-assistant-confirmations`, the human, `issued_at` (RFC 3339, nanoseconds) and the answers as canonical JSON, or `ants-assistant-pre-allow`, the human, the assistant, `issued_at` and the rules as canonical JSON, each on a line of its own. A reader honours one as it honours a grant: the key names the human, `jwt` is a device of the human's under the reader's account, it made `signature`, `issued_at` is at most 5 min ahead and not before the human's newest record the reader saw.

The requester's daemon keeps the latest decision of each assistant held on each request it waits on, from its watch of `ants_humans`. It applies one as soon as the grant still names the assistant and the human's answer to that act (the request, the assistant and the verdict) is `confirm`, or a pre-allow rule covers it; a `deny` drops it. A human's own stored decision coming first wins. Withdrawing or replacing the assistant drops the decisions the daemon holds of it at once. The request's status reports the decision as the human's (`decided`, `by: human`, `decider: <human>`) with `via: <assistant>`, which `ants watch` prints as `by alice via pa`. The CLI reads the same records, unverified, to tell such a request decided: `ants tools list` and `show` and the approvals view show it decided by `pa for alice`, `ants inbox -f` prints a line when a decision is held, and `ants chat` home shows it on the request: `pa chose allow-once for alice: o lists it`, the page `o` opens confirming or denying it.

An assistant has no right to publish decisions on `ants.approvals.*.*` (see [wire ACLs](#wire-acls-and-verification-invariants)): a decision stored there with `on_behalf_of` decides nothing, and would keep its human's own from being stored. Its admin orders are held by the machine's daemon as in [an assistant's orders](#an-assistants-orders).

#### Tools acting for its human

An assistant's harness sessions get, beside the other [MCP tools](architecture.md#mcp-tools), tools that act for its human, while the human's grant, read from the daemon's watch of `ants_humans` and verified as in [assistant grant](#assistant-grant), names the ant. Listing the tools leaves them out otherwise, and each call checks the grant again: a withdrawal or a replacement removes them from the next listing and refuses every call at once (`the grant of alice no longer names pa: nothing is done for alice`), on connections already open too, and a later grant brings them back.

| Tool | What it does for the human |
|---|---|
| `human_queue(thread?)` | Read what the human's home in `ants chat` shows from the last 7 days: questions ants asked it not yet answered, tool requests waiting for its decision or its stand-in's (`<ant>/<id>`, the tool, its options and expiry, and whether the assistant's decision on it is held), and messages to it, not from the assistant, after its read marker, leaving out threads marked done since their last message, at most 30 of each, with their message ids and threads. With `thread`, the messages to and from the human on that thread. |
| `answer_for_human(message_id, answers)` | Answer the questions of a message to the human, an answer for each in order (an option's number, numbers joined by commas where several may be picked, or typed text), on the questions' thread. |
| `send_for_human(to, text, thread?, plaintext?)` | Send a message to an ant or another human, on `thread` or a new one; no attachments. |
| `post_for_human(channel, text, thread?)` | Post in a channel the human is a member of, on `thread` or starting a new one, with a human's fresh turn budget. |
| `notes_for_human(thread, text)` | Post to the notes of a thread, with the fresh turn budget a human's post gives them (as `ants notes THREAD TEXT`). |
| `react_for_human(message_id, reaction, remove?)` | Add or remove a reaction to a message to or from the human. |
| `title_for_human(thread, title)` | Set the title of a thread of the human's (as `ants thread title`). |
| `done_for_human(thread)` | Mark a thread of the human's done (as `ants thread done`). |
| `decide_for_human(request, verdict)` | Decide a tool request waiting for the human (`allow_once`, `allow_always`, `reject`). |
| `order_for_human(ant, machine, op, changes?)` | Send an [admin order](#an-assistants-orders) to an ant on a machine (`pause`, `resume`, `restart`, `restart_now`, `read_settings`, `read_memories`, or `set` with `changes`: each a dotted `field`, its new `value` or none to remove it, and the `expected` value, or `expected_digest` of a secret, as `read_settings` shows it), held by the machine's daemon until the human confirms it. |
| `queue_for_human(ant)` | List the messages waiting for the ant as `ants queue ANT` does: those its daemon holds, those awaiting redelivery, and up to 50 of the inbox messages and channel posts waking it still in the stream, read from where the daemon's answer says its consumers stand, each with its id, thread, sender, age and place (withdrawn ones say by whom), and how many more wait unlisted. |
| `cancel_for_human(ant, thread)` | Cancel the prompt an ant runs on a thread, as `ants cancel` does. |
| `withdraw_for_human(ant, message_id)` | Withdraw a message waiting for an ant before it is prompted with it, as `ants withdraw` does; while no daemon of the ant serves, only a message of the human's to the ant, by a record the daemon honours later. |
| `mark_for_human(thread, mark)` | Pin, unpin, archive or unarchive a thread for the human (`pin`, `unpin`, `archive`, `unarchive`), as `ants thread pin` and the others do. |
| `snooze_for_human(thread, duration?)` | Snooze a thread from the human's home in `ants chat` for `duration` (`1h` by default, at most as long as `ants chat` allows), or wake it with `off`. |
| `describe_channel_for_human(channel, description)` | Set the description of a channel for the human (as `ants channel set --description`), or clear it with an empty one, through the channel manager, which honours the request only while the human's grant names the assistant and announces the change on the channel. |

Each act goes under the assistant's own name with `on_behalf_of` the human: a message (an answer, or a decision, carried by an `Envelope`), a channel or notes post, a reaction, a title, a done mark. An answer counts as the human's for the question it answers, which takes it out of the queue; the asking ant's daemon tells the human of it, and of a message sent to an ant, as in [acting for its human](#acting-for-its-human). For a message to another human, a channel or notes post, which every daemon sees, and a reaction, a title and a done mark, which no daemon receives, the tool tells the human itself, with a message in its inbox from the assistant (`[ants] pa, as the assistant of alice, ...`, with no `on_behalf_of`), on the human's activity thread of the day as in [acting for its human](#acting-for-its-human). A decision goes to the requesting ant's inbox, never `ants.approvals.*.*`, and is held there until the human [confirms it](#confirming-an-assistants-acts) or a pre-allow rule covers it; an admin order, which the tool tells the human of, likewise waits held by the machine's daemon.

A pin, an archive or a snooze for the human goes, by compare-and-set, into keys of the assistant's own in `ants_threads`, `marks.<human>.<assistant>` and `reminders.<human>.<assistant>` (in the format of the human's `marks.<human>` and `reminders.<human>`, of which only the snoozes count), which only the assistant and the human write, and the tool tells the human of it. The human's devices read them beside the human's own and honour them only while the human's grant names that assistant, verified as in [acting for its human](#acting-for-its-human), checking the grant afresh as it changes or the assistant's credentials are revoked; a pin or archive counts only on a thread the human's own marks neither pin nor archive, a snooze only while the human's own snooze of the thread is absent or past, and the assistant's keep marks never count. The human's own pin, archive, unpin or unarchive of the thread drops the assistant's pin and archive of it, and the human's own snooze or wake drops the assistant's snooze. So the assistant changes none of the human's own entries, whatever its harness writes with its credentials: the tool refuses a change to a thread the human marked or snoozed itself, and readers never take the assistant's keys for the human's.

A cancel or a queue request for the human goes on a subject naming the assistant (`ants.cancel.<ant>.<thread>.<assistant>`, `ants.queue.<ant>.<assistant>`, `by` the assistant and `on_behalf_of` the human), which no human's `ants.cancel.*.*` or `ants.queue.*` reaches; a withdrawal is a cancel request carrying `withdraw` (the message id), so the ant's daemon marks the message withdrawn in `ants_attempts` (`on_behalf_of` in the mark) rather than the assistant. The ant's daemon answers only a request whose claim it honours, as in [acting for its human](#acting-for-its-human), ignoring with a warning a request on such a subject claiming no human or one forged; for a prompt cancelled or a message withdrawn it tells the human, as for a message, and the cancelled prompt's sender reads `[ants] The prompt was cancelled by pa, the assistant of alice.`. `withdraw_for_human` finds the message's thread among the messages waiting for the ant, as `queue_for_human` lists them, else among the human's messages to the ant, and refuses a running one or one awaiting redelivery still `started`; one awaiting a retry after a failed attempt, or held for a sign-in or a provider limit after its tools ran (`retrying`), is withdrawn as `ants withdraw` withdraws it. While no daemon of the ant answers, it withdraws a message of the human's to the ant (sent by the human, or by the assistant for it) by a record instead: it creates `<ant>.msg.<id>.<assistant>` in `ants_attempts` (a `withdrawn` mark naming the assistant as `by` and the human as `on_behalf_of`), a key no human and no other assistant writes, then reads the message's mark. A mark stored before the record (the message taken up, or finished) or a withdrawal ends it: the tool says so and deletes the record; a `retrying` mark does not, as the redelivery claims `started` after the record. Otherwise it holds: a daemon of the ant taking up a message of the human's (its sender, or the human it was sent for) reads the key of the human's assistant after claiming `started`, and honours a record stored before that claim, its `by` the key's assistant and its `on_behalf_of` the message's human, only while the human's grant names the assistant, verified as for a cancel request: it rewrites the mark to the withdrawal (compare-and-set on the `started` claim), replies as for any withdrawal, and tells the human, as a live daemon does, when the reply goes to someone else. As both are ordered by their stream sequence, a record stored after the claim is too late for both the daemon and the tool. Before `send_for_human` sends to an ant, it records the human as the thread's owner for that ant under `<thread>.<ant>.<human>.<assistant>` in `ants_owners` (first record wins, on the hub only: no outbox holds it), which daemons take as the human's record only while the human's grant names that assistant.

Sealed messages are read and sent, and titles sealed, only while the grant [enrolls the assistant as a device](#assistant-as-a-device):

- `human_queue` opens the human's sealed messages for the assistant, and shows `[sealed]` for one it cannot open (no enrollment, or a message sealed before it) and `[forged]` for one failing its sender check.
- `send_for_human` seals a message to a human for the recipient's and the human's devices, refusing without the enrollment; `plaintext: true` sends it unsealed. Its notice to the human never quotes a sealed text.
- `title_for_human` seals the title of a thread carrying sealed messages for the devices of the human, the assistant's among them, and of the other party of its first sealed message, as `ants thread title` seals one, refusing without the enrollment; its notice to the human never quotes a sealed title.

The tools need no right beyond the [assistant's](#wire-acls-and-verification-invariants): reads of the `ANTS` stream and `ants_read` marker of its human, puts of `ants_threads` titles and done marks and of its own reactions, reads of `ants_devices`, puts of its own `marks.<human>.<assistant>` and `reminders.<human>.<assistant>` in `ants_threads`, cancel and queue requests on the subjects naming it, the withdrawals it records under keys naming it (`<ant>.msg.<id>.<assistant>` in `ants_attempts`, with the direct get of message marks a human holds), and owner records under the keys naming its human and it. `order_for_human` publishes on `ants.admin.<machine>.<ant>`, which an assistant may for its human's orders only, as its machine's daemon refuses any other.

## Adding an ant

`ants add` generates a user NKey on the target machine (`<ant>.nk` at mode `0600`, or seed straight into the OS store with `--store-key`), appends `[[ant]]` to `config.toml`, writes `<ant>.creds` once signed, and reloads `ants.daemon` / `ants-daemon`:

```sh
# Out of band
ants add dev-c --workdir ~/src/app                                # prints public key U...
ants auth user dev-c --public-key U... --js-domain hub            # auth machine: prints JWT
ants add dev-c --jwt eyJ...                                       # accepts JWT, file, or '-'

# Over NATS (direct or through leaf nodes)
ants auth enroll dev-c                                            # auth machine: enroll-dev-c.creds (default --ttl 1h; 0 = none)
ants add dev-c --workdir ~/src/app --enroll enroll-dev-c.creds    # target machine: waits for approval (--hub URL overrides --nats)
ants enroll list --js-domain hub                                  # auth machine
ants enroll approve dev-c --js-domain hub                         # or: ants enroll reject dev-c [--reason TEXT]
```

On the machine holding the account key, `ants chat` lists the pending requests too, on home and on the credentials page (`c`), where `a` then `y` approves one and `r` then `y` rejects it. Elsewhere, home and the credentials page name the machine holding the key, as `ants signer` there records it (`ants machines` prints it too): each time it connects, at start and every 5 minutes, the signer puts the `_account` key of `ants_machines` (`AccountHolder`: `machine`, from the `[host]` table of its config file, else its top-level `machine` when that is a machine name, else the first label of the host name, `hostname`, `version`, `updated_at`). Only credentials signed with the account key write that key (no machine name starts with `_`, so no host credentials do); humans read it with the rest of the bucket. Without a signer, the page says the key is where `ants auth init` ran.

With `--home` naming the home of an earlier ant of another name, as after `ants auth revoke`, the new ant keeps that ant's sense data: `ants add` lists the earlier name in the home's `.sense/names` ([sense.md](sense.md#identity)).

`ants add --enroll` repeats its request every 5 s and stops with an error at a rejection, when the enrollment credentials expire, or when the server refuses them (revoked), even while the server is unreachable.

Behind a leaf node (`~/.config/ants/leaf.conf` or `--leaf-config`), `ants add --enroll` signs the request with the leaf uplink key; `ants enroll approve` renews the leaf uplink JWT (up to the 252 KiB limit, ~44 ants with a domain or ~47 without; beyond it the approval fails before anything is signed or recorded), records the ant in `issued.jsonl`, admits it to `ANTS_IN` outbox sourcing, and `ants add` has the leaf node reconnect its uplink with the renewed credentials, by a reload keeping local connections (`ants enroll` behind a leaf requires `ants auth leaf --enroll-approver`). After out-of-band `--jwt` behind a leaf, run `ants auth leaf MACHINE --add-ant NAME` and `ants leaf outbox MACHINE`. See [transport.md](transport.md#enrollment-behind-a-leaf-node).

### Host credentials over NATS

On a machine without host credentials where the daemon looks for them (the `[host]` table's `creds`, else `~/.config/ants/auth/host.creds`), `ants add --enroll` (and `ants ant import --enroll`) asks for the machine's [host credentials](#machine-host-credentials) in the same request: it generates a second NKey (kept as `host.nk` beside the credentials until the answer) and asks for `host-<machine>`, the machine being the `[host]` table's `machine`, else the leaf node's machine behind one, else the config's top-level `machine` when it is a machine name, else the first label of the host name; a table naming another machine than the leaf's asks for none. `ants enroll list` and `ants chat` name the machine whose host credentials the request asks for, and the human approving the ant grants them too, signed as `ants auth host` would (never expiring, recorded in `issued.jsonl` as kind `host`); `ants enroll approve --no-host` approves the ant alone. `ants add` writes them where the daemon looks for them, and the daemon's reload starts the host connection with them. Admin orders never grant host credentials: the machine asking holds its own.

The machine name is bound as tightly as the ant's: the enrollment key signs the machine and the host key with the rest of the request (`host_creds`), as does the uplink key behind a leaf node, so a request altered on the way is ignored; behind a leaf node, the uplink key's signature proves the leaf's machine, and only that machine's host credentials are granted through it. The approval still approves the ant but grants no host credentials (telling why, and to use `ants auth host MACHINE` if the machine needs them) when:

- the request comes through the leaf node of another machine, or, for a machine whose leaf node holds live uplink credentials, not through it;
- the team holds live host credentials of the machine for another key (revoke them first with `ants auth revoke --key U...` if the machine lost them);
- the host key is revoked, is the ant's key, or was issued under another name.

Otherwise an enrollment key names its ant only, so a human approving trusts the machine name the way `ants auth host` trusts the operator typing it: before granting, check that the request comes from that machine.

## Moving an ant to another bus

An ant moves between buses as a file ([config.md](config.md#exporting-and-importing-an-ant)), never with its keys:

```sh
ants ant export dev-c --move                  # old bus: writes ./dev-c.ant and marks dev-c moved
ants ant import dev-c.ant --enroll enroll-dev-c.creds  # new bus: identity, settings, memories and a new key
ants auth revoke dev-c                        # old bus, once the import succeeded: ends dev-c there
```

The import creates the ant's identity record with a KV create, refused when a record of the bus holds its name or its
id, so no bus holds two copies of one ant; on one bus, `--as NEW` refuses too while the old record stays. `ants auth
revoke` of the ant deletes its record, after which its id may come back. Until then the moved mark keeps every daemon
of the old bus from serving it; `ants ant unseal NAME` undoes a move. Nothing signs the file: whoever carries it is
trusted with the ant's memories. Its sense part is checked, its hashes and the signatures of its sense log's events
against the old bus's account, and vouched for on the new bus by an event signed there
([config.md](config.md#senses-part)).

## Registering humans

A person joins the team as a human without the operator of the account-key machine issuing credentials: `ants login` on the person's machine asks `ants signer` on the hub for a new device's credentials, the signer has the person sign in to GitHub, checks the GitHub user against the team's registration policy, binds the human name to that GitHub user and signs.

1. **Operator, once:** on the account-key machine, issue the public [bootstrap credentials](#bootstrap-credentials) (`ants auth bootstrap`) and share `bootstrap.creds`; give the config file of `ants signer`, which connects to the hub, a [`[registration]`](config.md#human-registration) table naming the team's GitHub OAuth App, the policy and the signer's GitHub token.
2. **Person:** `ants login --hub URL --name NAME --bootstrap bootstrap.creds` generates the device's NKey and [encryption key](#device-encryption-keys) and asks for credentials.
3. **Signer:** starts a GitHub device flow ([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628)) and answers with GitHub's sign-in page and a user code, which `ants login` shows.
4. **Person:** signs in to GitHub in a browser and enters the code, letting the team's OAuth App read memberships and email addresses (scopes `read:org user:email`).
5. **Signer:** reads the GitHub user's numeric ID, login and verified email addresses with the user's token, and the memberships of the policy's organizations and teams with its own token (the user's without one), then drops the user's token: it is never sent or stored. A user the [policy](#registration-policy) admits is signed at once; anyone else waits for a human of the team to approve.
6. **Signer:** checks that the name may be [bound](#github-bindings) to that GitHub user, then signs a human's credentials for the device's NKey, binding its encryption key, for the signer's JetStream domain and valid for the policy's `ttl` (default 30 d). `issued.jsonl` records them with the label, the GitHub user and the grant.
7. **Person:** `ants login` writes `~/.config/ants/auth/NAME.creds` and, when `[cli]` names no credentials yet, points it at them, so `ants` commands act as `NAME`.

`ants auth user NAME --human` still issues a human's credentials by hand, on the account-key machine.

### Bootstrap credentials

```sh
ants auth bootstrap [--ttl 0] [--out FILE]                 # bootstrap.creds (mode 0644; default: no expiry)
ants auth revoke bootstrap --nats wss://hub.example/nats   # withdraw them; reissue with ants auth bootstrap
```

Bootstrap credentials (user `bootstrap`) are public, meant to be shared with whoever may join: they only publish registration requests on `ants.login.*` and hear the answers on `ants.login.*.reply`, with messages of at most 4 KiB, and have no JetStream access, so they read and write nothing stored ([transport.md](transport.md#client-connections)). Holding them admits no one: every registration still needs a GitHub sign-in that the policy or a human admits. They are recorded in `issued.jsonl` (kind `bootstrap`) and revoked like any key. Registration happens on the hub only: leaf uplinks never carry `ants.login` subjects, so both `ants login` and `ants signer` connect to the hub.

### Signing in with `ants login`

```sh
ants login --hub wss://hub.example/nats --name alice [--label workstation] [--store-key] [--bootstrap FILE] [--github-url URL]
```

`--bootstrap` defaults to `~/.config/ants/auth/bootstrap.creds`, and `--github-url` to `https://github.com`: the GitHub trusted to sign in at, a GitHub Enterprise Server's `https://HOST` when the hub's `[registration]` names one. `ants login` makes the device's NKey and encryption key in memory and sends a registration request on `ants.login.<name>`: the name asked for, the NKey's public key, a one-off X25519 reply key, the encryption key, the label, and its making and expiry times (at most 15 min apart), signed by the NKey. Requests are core NATS messages, stored nowhere: `ants login` repeats its request every 5 s until an answer settles it, the request expires (15 min) or Ctrl-C. `ants signer` answers each repeat on `ants.login.<name>.reply` with what it has for that key: the request's public key in the clear, and the answer sealed to the latest reply key, naming the signer's sealing key, so other holders of the bootstrap credentials hear it but cannot open it:

- `verify`: sign in to GitHub at the URL with the user code, before the time given. `ants login` shows them only when the URL is the device login page of `--github-url` (`https://github.com/login/device` by default), so a hostile hub cannot send the person to another page; any other URL stops the login without showing or naming it.
- `waiting`: the GitHub user who signed in (login) is outside the policy, and a human of the team decides; `signed` or `refused` follows.
- `signed`: the human's credentials (a user JWT).
- `refused`: why, such as registration not enabled, the signer busy, a key already issued, a name not that GitHub user's to hold, a human's rejection or no decision in time.

The signer runs one GitHub device flow per key, and at most 10 registrations at once (those waiting for a human included), refusing more as busy; each repeat of a key gets the same user code. Requests that are malformed, unsigned by their key, expired, for another subject or unlike the earlier request of their key get no answer. A key whose registration ended gets the same answer until its request expires; another attempt uses a new key.

`ants login` takes signed credentials only when issued to its key, for a human of the name asked, binding its encryption key, by the account of the bootstrap credentials. They go to `~/.config/ants/auth/NAME.creds` (mode `0600`, with the encryption key seed as an `ANTS XKEY SEED` block), replacing an earlier file, whose credentials stay valid until they expire or are revoked: `ants login` prints `ants auth revoke --key K --earlier` for their key K, which revokes them and the live keys they were renewed from. With `--store-key` both seeds go to the [OS credential store](#private-keys-in-the-os-credential-store) instead, and the file naming them is written once they read back and authenticate at the hub (with a warning when the hub does not answer). When `[cli]` in `ANTS_CONFIG` (`~/.ants/config.toml`) names no `creds`, it gets `creds` set to that file and, when it names no `nats`, `nats` set to the hub. A refusal, expiry or Ctrl-C leaves no key and no file behind.

### Registration policy

The [`[registration]`](config.md#human-registration) table of the signer's config file, reread for each request, decides who is signed at once, with the first grant that applies recorded with the device in `issued.jsonl`:

- `org`: an active member of a listed GitHub organization;
- `team`: an active member of a listed team (`org/team`);
- `email-domain`: a user with a verified email address in a listed domain (that exact domain, not its subdomains);
- `approval`: anyone else, once a human of the team allows it.

For a GitHub user outside the policy, `ants login` shows that it waits while the signer asks the humans with an approval request of the reserved user `signer`, on a thread of its own (`register human NAME: GitHub user LOGIN (id N), outside the registration policy`, its input naming the name, GitHub user, label and key), offering `allow_once` or `reject`. It shows in `ants tools`, `ants inbox -f`, `ants dash` and all `ants webhook serve` notification sinks, and any human decides it (`ants tools approve signer/<id>` or `reject`). The signer waits up to its `--approval-timeout` (default `15m`), at most until the request expires: once a human allows it, the device is signed with the grant `approval`, naming that human; a rejection or no decision in time refuses it. At most 3 registrations wait for a human at once (more are refused). Waiting registrations drop on a signer restart, after which the next repeat of the request starts a new GitHub sign-in.

An approval stands for that GitHub user and name: the user's later devices of the name are signed at once, until `ants auth revoke NAME` withdraws it ([Offboarding](#offboarding)).

### GitHub bindings

A name registered with a GitHub sign-in belongs to that GitHub user's numeric ID for good, so a renamed GitHub account keeps its name:

- The first registration signed for a free name binds it. The same GitHub user registering the name again adds a device; another GitHub user asking for it is refused, and so is a GitHub user already bound to another name.
- `human`, the reserved names `bootstrap`, `channel-manager`, `revoked`, `signer`, `system-messenger` and `system-sage`, and names any key other than a human's was issued to (an ant, webhook, leaf node, enrollment, ...) are refused.
- A name holding human credentials but no binding (issued with `ants auth user --human`) is refused until the operator binds it:

```sh
ants auth user alice --human --github octocat [--config FILE]   # bind alice to GitHub user octocat, new device
```

`--github` looks the login up on GitHub (with the GitHub URLs and the signer's token of the `[registration]` table in `--config`, `ANTS_CONFIG` or the default config file when it exists; github.com without a token otherwise) and records its ID with the new device, under the same rules but binding a name that holds human credentials; on a name already bound to the same user it adds a device. A device issued this way has no grant, so `ants enroll renew` renews it like any other; the person's devices registered with `ants login` go through the policy.

The binding is recorded on each device's line in `issued.jsonl` with the grant and the GitHub login (as of the signing or latest renewal), so it is kept across renewals and revocations and in [backups](#backing-up-the-team-keys), and `ants auth devices` shows it ([Devices](#devices)).

### Lifetime and renewal

Registered credentials expire after the policy's `ttl` (default 30 d). Before then, `ants renew` (the `--creds` or `[cli]` credentials by default) renews them [over NATS](#renewing-over-nats), also behind a leaf node. `ants signer`, not `ants enroll renew`, answers the renewal of a device whose latest line in `issued.jsonl` has a grant, with the same `RenewReply` for each repeat, holding the JWT or `refused` with the reason, at which `ants renew` fails:

- `org` or `team` grant: the signer looks the GitHub user up by ID with its own token and checks the memberships of the policy, reread. A user still a member of a listed organization or team is renewed, with the grant the policy now gives and the current login. A user who is no longer one (who left, or whose organization or team the policy no longer lists), or no GitHub user any more, is refused, and every key of the name is revoked and the account pushed. Without a `[registration]` table or token, or when GitHub cannot tell, the renewal is refused alone: try again later. At most 10 checks run at once; more requests wait for their next repeat.
- `approval` grant: renewed while the approval stands; once withdrawn, refused, naming `ants login`.
- `email-domain` grant: refused, naming `ants login`, as only a new sign-in shows the verified email addresses: such a device registers again with `ants login` before its credentials expire.

A renewal keeps the credentials' lifetime, not the policy's current `ttl`. Expired credentials are not renewed: run `ants login` again, which adds a device for the same GitHub user while the policy or a standing approval admits it.

Credentials the signer signs or renews for a registration carry the user JWT tag `ants-registered`, which `ants enroll renew` leaves out, so the holder's renewal hints name the right path: `ants renew`, `ants doctor` and the warnings logged at connect name `ants signer` for them, `ants login` once they have expired, and `ants enroll renew NAME` only for credentials without the tag. The tag only guides the holder; the signer goes by `issued.jsonl`.

### Membership sweep

Between renewals, `ants signer` checks the memberships again every `sweep` of the `[registration]` table (default `6h`, the first sweep at start; `"0"` turns it off), for every name with live credentials (neither revoked nor expired) an `org` or `team` grant admitted: it looks the bound GitHub user up by ID with its own token, as a renewal does, one user per second. A user GitHub definitely finds no longer a member of a listed organization or team, or no GitHub user any more, loses every key of the name, as at a refused renewal. A name is kept whenever GitHub cannot tell (an error, a timeout or a rate limit), until the next sweep. Credentials of `approval` and `email-domain` grants, and devices issued with `ants auth user`, are not swept.

- **Off:** without the `[registration]` table, with `sweep = "0"`, without the signer's token (`token_file` or `token_store`), or with a policy listing no organization or team; `ants signer` prints why once and looks again every 10 min.
- **Seeing the policy:** each sweep first checks that the token sees every listed organization and team (`GET /orgs/ORG`, `GET /orgs/ORG/teams/SLUG`); otherwise the sweep is skipped with a message, as GitHub would then report every user a non-member.
- **Rate limits:** the sweep follows GitHub's `x-ratelimit-remaining` and `x-ratelimit-reset` headers, keeping the last 100 requests of each window for registrations and renewals, and waits out a `403` or `429` refusal (`retry-after`, or the window's reset), up to an hour at a time.

Each name revoked by a sweep or a refused renewal is printed, logged, and appended to `offboarded.jsonl` in the team directory (`at`, `name`, `github`, `by`: `sweep` or `renewal`, `reason`, `keys`), the account is pushed, and the revoked devices are recorded in the [directory of device keys](#directory-of-device-keys), as `ants auth revoke` does. A failed push or record names `ants auth push`.

### Offboarding

- **Revoking:** `ants auth revoke NAME` revokes every key of the name, closing its connections once the account is pushed, and withdraws an `approval` grant (the key's line appended again, marked `withdrawn`); revoking one device (`--device`) or key (`--key`) withdraws nothing. The binding stays, so the name remains that GitHub user's, who registers again only through the policy or a new approval. A user still in a listed organization or team, or with a verified email address in a listed domain, is signed again at once: remove the user there, or the entry from the policy, too.
- **Leaving an organization or team:** the next [membership sweep](#membership-sweep) (every `6h` by default), or the first renewal after the user left, whichever comes first, revokes every key of the name an `org` or `team` grant admitted. Without the signer's token, or with `sweep = "0"`, they stay valid until they expire. `ants auth revoke NAME` cuts them off at once.
- **Email domains:** an `email-domain` grant ends with its credentials, as only a new sign-in showing a verified address in a listed domain registers again.
- **Closing registration:** without the `[registration]` table the signer refuses every registration and every `org` or `team` renewal, and sweeps no memberships; revoking the bootstrap credentials keeps requests from reaching it. Registered devices stay valid until they expire or are revoked.

## Renewing over NATS

Valid, unrevoked credentials (ants, humans, webhooks, observers, `channel-manager`, and `leaf-<machine>` uplinks) can renew over NATS without copying files from the auth machine:

```sh
ants renew ~/.ants/dev-a.creds                                                             # target machine
ants renew ~/.config/ants/auth/leaf-worker-1.creds --creds ~/.config/ants/auth/alice.creds # leaf uplink via human creds
ants enroll renewals --js-domain hub                                                       # auth machine: list pending
ants enroll renew dev-a --js-domain hub                                                    # sign one (or --auto to sign continuously)
```

`ants renew` generates a local NKey, publishes signed `RenewRequest`s on `ants.renew.<name>` every 5 s, verifies the returned JWT, atomically replaces the `.creds` file (preserving OS credential store placement), and reloads `ants.daemon`, or for leaf uplink credentials reconnects the uplink by reloading `ants.nats` (or the nats-server an `ants daemon` runs from `leaf.conf`, [operations.md](operations.md#managed-nats-server)) with the `credentials` path respelled in `leaf.conf` (see [transport.md](transport.md#enrollment-behind-a-leaf-node)). For a human's credentials without an encryption key, `ants renew` also generates one and asks for it bound (the request's signed `xkey`), keeping its seed beside the new NKey seed; credentials that hold one keep it. `ants enroll renew` refuses a requested key for credentials of others than humans or already binding one, and preserves role, device, encryption key, domain, webhook destinations, leaf members and TTL while stamping the current permissions version, records `renewed_from` in `issued.jsonl`, and prints `ants auth revoke --key K --earlier` for the old key K, which revokes K and the live keys K was renewed from, never the new key. `ants enroll renew --auto` continuously approves valid unrevoked requests (reconnecting every 5 m to refresh `revoked.json`); on the account-key machine, the credentials page of `ants chat` (`c`) signs one with `a` then `y`. Host, bootstrap, enrollment, leaf system and leaf store, expired, or revoked credentials must be reissued via `ants auth`.

Credentials a registration granted (a device registered with `ants login`, whose latest line in `issued.jsonl` has a grant) are renewed by `ants signer` instead, while the grant holds, and `ants enroll renew` and `ants enroll renewals` leave them to it (see [Lifetime and renewal](#lifetime-and-renewal)).

## Credentials across upgrades

Each user JWT carries `ants-perms:<n>` (current: `8`), required on every user JWT `ants auth` issues, and live daemons, webhooks, schedules and `ants channel serve` publish their running `ants` and `perms` versions. The version goes up whenever the permissions of a kind of credentials change. Connecting with outdated or soon-to-expire (< 7 d) credentials logs a warning with the exact renewal command (credentials newer than the running ants ask for an upgrade of ants); `ants doctor` (**versions**) verifies that all live services run the current permissions version before rights an older version had are withdrawn by renewing. Leaf uplinks whose members' rights changed need renewal and `ants leaf outbox` too.

## Private keys in the OS credential store

`ants keys store` moves a `.creds` file's NKey seed, and the seed of its [encryption key](#device-encryption-keys) when it holds one, into the OS credential store — macOS login Keychain (service `ants`), Linux Secret Service via `secret-tool` (`libsecret-tools` / `libsecret`), or Windows Credential Manager (`ants:<public_key>`) — after reading the seed back and authenticating against `--nats`, leaving only the JWT and public key reference in the file:

```sh
ants keys store ~/.config/ants/auth/alice.creds ~/.ants/dev-a.creds   # default: --creds
ants keys unstore ~/.ants/dev-a.creds                                  # write seeds back into file
ants keys remove ~/.ants/dev-a.creds                                   # delete file and stored seeds (does not revoke)
```

`ants keys remove` prints `ants auth revoke --key K --earlier` for the key K of each file removed, to run on the machine holding the team keys: it revokes those credentials and the live keys they were renewed from.

`ants add --store-key`, `ants auth user --store-key`, and `ants auth channel-manager --store-key` write new seeds straight into the store without touching disk (printing the approved JWT if `ants add --enroll --store-key` fails so `--jwt` can finish later). `ants keys store` refuses leaf uplink credentials (read by `nats-server`), team keys (`operator.nk`, `account.nk`, `store.nk`, `system.nk`), and ephemeral in-memory keys.

Platform notes (where no unlocked store is available, keep `0600` file-backed `.creds`):

- **Services & macOS:** `ants daemon` (and its schedules), `ants webhook serve` (webhooks and human notifications), and `ants channel serve` retry locked/unavailable stores at startup (`1s` doubling to `30s`), failing immediately only if the entry is missing or mismatched; one-shot CLI commands fail immediately. On macOS, replacing `~/.cargo/bin/ants` (`cargo install`) prompts Keychain access again: grant **Always Allow** in a GUI session and restart the service.
- **Linux Secret Service:** desktop login unlocks the keyring (`secret-tool` times out after 60 s if locked; `ants` queries D-Bus via `busctl`, `gdbus` or `dbus-send` so locked collections never masquerade as missing entries).
  - *KDE Wallet:* requires running `kwalletd6`/`kwalletd5` plus `libqca-qt6-plugins`; closed wallets prompt on read and fail deletes as locked until opened.
  - *KeePassXC:* enable **Secret Service Integration**, expose a group in database settings, and disable **Confirm when passwords are retrieved by clients** (and deletion confirmation if recycle bin is off) for unattended use.
  - *Headless systemd / WSL 2:* requires `systemd --user` and `$XDG_RUNTIME_DIR/bus` (`dbus-user-session`; `[boot] systemd=true` in `/etc/wsl.conf` on WSL 2, which cannot access the host's Windows Credential Manager). System units, cron and `sudo` have no session bus. Unlock over SSH after boot via `printf '%s' "$PASSWORD" | gnome-keyring-daemon --replace --unlock --components=secrets`, or keep file-backed `.creds` rather than storing a keyring password on disk.
- **Windows:** Credential Manager entries require an interactive/password logon; key-authenticated SSH sessions, other accounts, or passwordless scheduled tasks fail with error `1312` — use file-backed `.creds` there.

## Wire ACLs and verification invariants

- **Subject-pinned senders:** ants publish only under their own final subject token (`ants.inbox.*.<self>`, `ants.notes.*.<self>`, `ants.chan.*.<self>`, `ants.dead.<self>`, `ants.chanadm.*.<self>`, `ants.timeline.*.<self>`, plus `ants.out.*` on leaves).
- **Subject-pinned webhooks:** a webhook's or schedule's credentials publish only on subjects of its own, one token longer: `ants.inbox.<ant>.<self>.webhook` and `ants.chan.<channel>.<self>.webhook` for its destinations, and never on a subject an ant sends on; no ant's credentials publish on these. Messages and posts carry `webhook: true` exactly on these subjects, and readers take one whose flag disagrees with its subject as forged (a daemon dead-letters such a message unprompted). So the subject, which the issuing human's credentials fix, tells a webhook from an ant: nothing a webhook writes, its `<self>.webhook` key in `ants_webhooks` included (only the version it runs), makes it pass for an ant, nor an ant for a webhook.
- **Payload checks:** readers verify payload `from`/target fields against the NATS subject or KV key (`ants watch` and `ants thread` mark mismatches `forged`). Only humans publish under arbitrary inbox senders (`ants dead replay`), write `ants.approvals.<ant>.<id>` (any human may decide any ant's request, so a [stand-in](webhooks.md#stand-in) needs no extra rights; the decision's `by` is informational, not pinned by the subject), send `ants.cancel.*` / `ants.queue.*` / `ants.trail.*`, write `ants_humans` (entries, and only their own `<human>.>` keys such as the [assistant grant](#assistant-grant)) / `ants_channels` (with `channel-manager`), or call `STREAM.MSG.GET` / `$JS.API.DIRECT.GET.ANTS`.
- **Messages a stream relayed:** nats-server checks a publisher's rights on the subject it publishes to, never on the reply subject it names, and a stream answers a direct get by sending the stored message, the headers and payload its writer chose, to that reply subject from inside the account. So credentials that put and direct-get any key (an ant's own keys of `ants_trail_runs`, `ants_sessions` and `ants_attempts`, among others) have the server deliver a message of their choosing on any subject: into `ants_trails` or another conductor's keys of `ants_trail_runs`, onto `ants.trail.<ant>` or `ants.savetrail.<ant>`, or into an inbox, past every subject permission above. Such a message carries the stream's `Nats-Stream`, `Nats-Subject` and `Nats-Sequence` headers after those its writer stored, and a consumer's delivery, to a reply or deliver subject its creator chose, a `$JS.` reply subject; no client publishes either. The server also answers a reply subject itself, from inside the account and with no header: a publish into a stream with its ack (`{"stream":…,"seq":…}`, or a refusal `{"error":{"code":…}}`), a JetStream API request with its answer (`{"type":"io.nats.…",…}`), a consumer's ack of a message with an empty message, and a direct get finding nothing with a status, which a stream stores as an empty message without the status. So credentials that may publish one message into a stream (an ant's, a webhook's or a schedule's, each under its own keys or subjects) have such an answer stored on any subject. The readers of saved trails, run records, trail and save requests and inboxes refuse them: a direct get of an entry or of `ANTS`, single or batched (each bucket read through `DirectKv`, `ants trail show`, `ants trail runs`, `ants trail follow` and the CLI's other batched reads of buckets, read-backs of the stream by humans and assistants), takes no message with more than one value of any of these headers, its own get adding one, nor one with no header of its own (beyond those its get adds) whose payload is empty or such an answer; a consumer's reader takes none with any, nor such an answer (an ant's daemon dead-letters such an inbox message unanswered, and read-backs through an ant's reader consumers and their spares skip it); and a subscriber of `ants.trail.<ant>` (the conductor's daemon), `ants.savetrail.*` (`ants signer`) or a live inbox drops one with any of them or with a `$JS.` reply subject (a live inbox takes the stream's republished copies only with its single `Nats-Stream` and `Nats-Subject`). Beyond trails and inboxes, every other reader is guarded the same way: the key-value readers of `ants_humans` (the humans registry, assistant grants and consents), `ants_channels`, `ants_colony` (registrations and turns), `ants_chains`, `ants_devices`, `ants_identities`, `ants_notify`, `ants_read` and the other buckets read an entry by a direct get and take a relayed message on a key as its removal, and their watches skip a change whose stored message is relayed; the subscribers of approval decisions, `ants.cancel.*`, the queue, status and notes, channel rooms and posts, renewals, enrolment and login, `antreq`, reactions and channel-manager requests, trailed runs and trail control, and every `_INBOX` reply to a request drop a relayed message, a `$JS.` reply subject included; and the stream readers take no relayed message: a channel post's admission (`admit_post`, which drops it unanswered), the dead-letter reader and the advisories it buries, the done reader of `ants_threads`, notes read-backs, the stored decisions read by an ant's daemon, `ants signer` and the tool-request commands (`ants tools`), links and reactions read back, hooks' observers and notifications, the presences `ants chat` reads to show who is online (a key whose last message was relayed counts as gone), and the direct gets of `ANTS_SENSE` ([sense event logs](#wire-acls-and-verification-invariants)). A lint (`clippy.toml`'s `disallowed-methods`) refuses the unguarded key-value reads, watches, subscriptions and requests of `async-nats` outside tests, so a new reader goes through `bus::relayed`.
- **Trail buckets past relays:** a message a stream or the server sent onto a key, a relay or a stored answer as above, still stands as the key's last message, which a bucket of history 1 would keep in place of the writer's entry. The four trail buckets (`ants_trails`, `ants_trail_runs`, `ants_trail_tips`, `ants_trail_ratings`) therefore keep every message of a key rather than the last alone, and their readers take the last message the key's writer put, skipping relayed messages and stored answers: listings fold every message of the bucket, and a single get whose last message was relayed reads the key's earlier messages, by direct gets naming no subject for credentials allowed them, and, for a conductor's daemon reading its own run records, through the consumer `runsread-<ant>`, which ant credentials may create on `ants_trail_runs` filtering their own keys only, take messages from and delete. A compare-and-set write still expects the key's last message, a relayed one too, so a relay in between makes it read again rather than lose its entry; creating a key whose messages are all relayed succeeds. A tip's retirement key holding a message no reader can parse counts as a retirement by a human.
- **Scoped reads & key privacy:** stream info on `ANTS`, `ants_sessions`, `ants_attempts`, `ants_owners`, `ants_webhooks` and `ants_trail_runs` exposes subjects/keys (those of `ants_trail_runs` name the threads of each conductor's runs and steps, `<ant>.steps.<step thread>` and `<ant>.on.<thread>.<step thread>`), so only humans hold `STREAM.INFO` there, and assistants, which read what a human reads (below). Ants discover JetStream via `CONSUMER.INFO` on `inbox-<ant>`, read where `inbox-<ant>` and `chan-<ant>` stand (`CONSUMER.INFO`, no other consumer's) to answer `ants queue`, pin consumer filters in the create subject (`inbox-<ant>[_1..2]`, `chan-<ant>`, `chanread-<ant>[_1..2]`, `notes-<ant>[_1..2]`, `deadread-<ant>`, `sentread-<ant>` on `ants.inbox.*.<ant>` or `ants.timeline.*.<ant>`, `done-<ant>` on `KV_ants_threads`), and read/write single keys via direct gets and plain publishes. Humans direct-get only spend keys (`*.*.spend`, `*.day.*`) in `ants_sessions`, message marks (`*.msg.*`) and `<self>.unserved.*` in `ants_attempts`, and only their own keys in `ants_read` (`<self>`, `<self>.chan`), `ants_presence` (puts; every human's is readable by direct gets and an ordered consumer, while ants read none), `ants_notify`, `ants_devices` (puts; all of it is readable), and `marks.<self>` and `reminders.<self>` (reminders and snoozes) in `ants_threads` (`title.*`, `summary.*` and `done.*` are shared across humans; ants access no other key of `ants_threads` than those below, nor others' `ants_reactions`). Before reminding a human of an escalation, a daemon direct-gets, read-only and one key at a time, `done.<thread>` and the human's own `reminders.<human>` in `ants_threads` (for its snoozes; the entry also holds the human's reminders and their notes, but not `reminders.<human>.<assistant>`), the human's inbox read marker `<human>` in `ants_read` (not `<human>.chan`) and its holds `<human>` in `ants_notify` (not `held.<human>`), so it stops once the human marked the thread done, read the escalation or muted the thread, and waits out a snooze; without stream info it reads them only for humans and threads it knows. A daemon also hears every marking of a thread done, through its ant's durable consumer `done-<ant>` of `KV_ants_threads`, whose filter `$KV.ants_threads.done.*.*` (the `done.<thread>.<mark>` entries a human or assistant puts before each done state) is pinned in the create subject, to tell its provider of the threads it holds a session of marked done ([lifecycle events](architecture.md#lifecycle-events)), and may delete that consumer and `chan-<ant>`, which it does as a retirement stops the ant: so it learns the ids of the threads marked done, as the notes it reads tell it those of the threads noted, and nothing else of the bucket. Ants direct-get `title.*` in `ants_threads`, read-only and one key at a time, so a daemon titles the [draft pull request](architecture.md#pool-worktrees-and-at-least-once-retries) of a thread's branch with the thread's title: without stream info an ant lists no key, so it reads only the titles of threads whose ids it knows, and a [sealed title](#sealed-messages-between-humans) shows it nothing but an empty `title`, so the pull request takes the thread's opening line instead. An ant's title suggestion travels as `title` on its own reply (inbox message, channel post or notes post), whose subject pins the sender; only a human's CLI stores it, and only on a `title.<thread>` key with no entry, not even a cleared title's delete marker.
- **Ordered consumers of buckets:** credentials that list or watch a bucket create its ordered consumers unnamed (`$JS.API.CONSUMER.CREATE.KV_<bucket>`). After a reconnect or missed heartbeats, async-nats deletes the old consumer by name and creates the next under a name, with a single filter in the subject (`$JS.API.CONSUMER.CREATE.KV_<bucket>.<name>[.<filter>]`, `$JS.API.CONSUMER.DELETE.KV_<bucket>.<name>`), so the same credentials hold both forms. The unnamed form already takes any filter in its body, so the named one reads nothing more; it also lets those credentials create a durable consumer of the bucket's stream, bounded by the stream's `max_consumers`.
- **Reactions for ants:** subjects cannot tie a reaction key (`<reactor>.<message>.<reaction>`) to the messages an ant reads, and the harness can read the ant's `.creds`, so ant credentials neither read nor write `ants_reactions` (human credentials write only their own keys). An ant asks only as itself: on `ants.reactions.<self>` for the reactions to a message, on `ants.reactions.<self>.react` to add or remove its own; it hears the answer on `_INBOX.<self>.reactions`, among its own reply inboxes, which only humans and `ants signer` publish to (adding no subject per ant to a leaf uplink). `ants signer` answers both in queue group `reactions`, with short-lived credentials it issues itself from the account key (adding to those of `ants enroll` stream info and direct gets on `ANTS`, every read and write of `ants_reactions`, and the reply subjects); `ants webhook serve` also answers listings with a `[[human]]` entry's credentials, which cannot write an ant's reaction. Either acts only when the first message stored in `ANTS` with that id (from 5 min before the time in its UUIDv7 to 24 h after, the duplicate window) is on a subject the ant reads: `ants.inbox.<self>.>`, `ants.inbox.*.<self>`, `ants.notes.>` or `ants.chan.>`. Senders choose ids, but no one learns an id before its message is stored, so a later copy stored under a readable subject grants nothing; any other message gets the same `unknown` answer as a missing one, and no change. A daemon without credentials, on an open server where every connection reads and writes everything, answers its ants in-process with the same check.
- **Attachments (`ants_files`):** a message carries only references (`attachments: [{id, name, mime, size, sha256}]`); the bytes sit in stream `OBJ_ants_files` as chunks on `$O.ants_files.C.<from>.<kind>.<target>.<id>.<n>`, where `<kind>.<target>` (`inbox.<to>`, `notes.<thread>` or `chan.<channel>`) follows the subject of the carrying message, so subject permissions confine them as they confine the messages. Every user writes chunks only under its own name (`$O.ants_files.C.<self>.>`, plus `ants.out.files.<self>.>` for a leaf outbox), each with `Nats-Expected-Last-Subject-Sequence: 0` when written directly, so stored bytes are never replaced, and with `Nats-Msg-Id` `<handle>.<n>`, so a copy sourced from a leaf outbox within a day is dropped as a duplicate ([transport.md](transport.md#store-and-forward)); the stream denies deletes and purges. Ants read by direct gets only `…C.*.inbox.<self>.>`, `…C.<self>.inbox.>`, `…C.*.notes.>` and `…C.*.chan.>`, with no stream info or consumer; humans read all, and alone create the store and update its sources (`ants leaf outbox`; an enrollment approver's uplink and `ants signer` too, on admitting a new ant). No Object Store metadata subjects are used, as their base64 names cannot be scoped. Readers check the bytes against the reference's size and SHA-256. The exports of providers that `export_provider` and `import_provider` orders carry by reference ([Admin orders](#admin-orders)) are stored as chunks on `$O.ants_files.C._admin.<id>.<machine>.<n>` (at most 64 MiB), `machine` the order's: humans write and read any, as any chunk, and a machine's host credentials write and read by direct get only those of their machine (`$O.ants_files.C._admin.*.<machine>.>`); no ant name starts with `_`, so no ant reaches them. Webhooks, observers, the channel manager and enrollment credentials get no access.
- **First-writer `ants_owners`:** written only by humans and ant-targeting webhooks (`<thread>.<ant>`, `Nats-Msg-Id: owner.<key>`), and by an assistant for its human (`<thread>.<ant>.<human>.<assistant>`, honoured only while the human's grant names the assistant). The stream enforces `discard_new_per_subject` with a 30 d duplicate window and denies deletes/purges, so first owner wins while outbox replays drop cleanly without stalling sourcing.
- **Assistants:** `Permissions::for_assistant` gives an assistant an ant's rights plus what a human reads and keeps of its own, under its own name: it watches `ants.>`, reads `ANTS` (stream info, `STREAM.MSG.GET`, direct gets) and the buckets a human reads, reading the stream back by direct gets as a human does (its daemon and CLI too), so it holds none of an ant's reader consumers (`notes-`, `chanread-`, `sentread-<assistant>` and the spares `inbox-`, `notes-`, `chanread-<assistant>_<n>`) but `deadread-<assistant>`, and no `notify-<assistant>`, titles threads and marks them done, keeps its own reactions and read markers, and reads every attachment and the directory of device keys. Of its human's state it reads, by direct gets, the read markers (`<human>`, `<human>.chan` in `ants_read`), `marks.<human>` and `reminders.<human>` in `ants_threads`, and `<human>.unserved.*` in `ants_attempts`, and writes none of them: it puts the marks and snoozes it sets for its human under `marks.<human>.<assistant>` and `reminders.<human>.<assistant>`, which the human's devices honour only while the human's grant names it and only where the human's own entries leave room; it keeps none of its own. It sends only as itself, so its acts are never indistinguishable from its human's: what it does for its human names the human in `on_behalf_of`, which readers honour only as in [acting for its human](#acting-for-its-human), and it puts only its own record in `ants_devices` (`<assistant>.assistant`). It gets none of a human's rights whose subject does not name who acts, as no reader could tell its act from its human's: `ants.cancel.*.*`, `ants.queue.*` and `ants.trail.*` (whose requests name the asker in `by`, which no reader checks), withdrawing queued messages (`*.msg.*` in `ants_attempts`), recording owners under `<thread>.<ant>` in `ants_owners` (and `ants.out.owners.*.*`), publishing dead letters, answering reactions or renewal requests. It cancels, asks for a queue and withdraws (through the ant's daemon, or, while none answers, by a record under `<ant>.msg.<id>.<assistant>` in `ants_attempts`, a key naming it) on subjects naming it instead, `ants.cancel.<ant>.<thread>.<assistant>` and `ants.queue.<ant>.<assistant>`, and records owners for its human under `<thread>.<ant>.<human>.<assistant>`, which readers check against the human's grant ([tools acting for its human](#tools-acting-for-its-human)). Nor does it decide on `ants.approvals.*.*`: it decides for its human in a message to the requester, held until the human confirms ([confirming an assistant's acts](#confirming-an-assistants-acts)), as readers ignore a decision stored there with `on_behalf_of`, and one stored there would keep the human's own (`ants tools approve`) from being stored. It publishes admin orders (`ants.admin.*.*`), which the machine's daemon applies only as orders for its human, held until the human confirms ([an assistant's orders](#an-assistants-orders)); on a leaf node, its uplink carries the right for an assistant member. Nor does it change the team: no writes to `ants_humans` (where grants stand) or `ants_channels` (it describes a channel for its human by a request to the channel manager, which reads the human's grant and the assistant's record in `ants_devices` before applying it), no stream or bucket created or updated, no message deleted, no device's rights (`ants_devices` puts but its own record, `ants_presence` puts, `ants_notify`), no human's inbox, nothing of the account key.
- **Admin orders:** only humans and assistants publish `ants.admin.<machine>.<ant>`, for any machine and ant; ants, webhooks and observers send none, and an assistant's order is applied only for its human's consent. A machine's host credentials take only consumer `admin-<machine>` and write only outcomes of orders to their machine (`$KV.ants_machines.<machine>.>`). Humans read outcomes by batched direct gets and write none. A host reads `ants_humans` to check an assistant's orders against its human's grant and consents, and writes none of it. The daemon trusts no sender for the role: it verifies the admin's signature, credentials, tag and revocation itself ([Admin orders](#admin-orders)). Any human may publish an order, so a human without the role can only make a daemon record refusals. Host credentials publish enrollment requests for any ant name and hear every answer, as subjects cannot tie them to their machine's orders; `ants signer` signs or revokes on such a request only for an admin's order to the machine whose host credentials signed it, about the ant it names, so a host without one gets refusals only.
- **Sense event logs (`ANTS_SENSE`):** only machine host credentials (and a leaf uplink carrying them) reach the stream: they create it (`$JS.API.STREAM.CREATE.ANTS_SENSE`, withheld from humans so none can create it with a republish or leaking source), append to `ants_sense.*` (outside `ants.>`, invisible to human `ants.>` subscriptions), and read by direct gets, with no stream info, consumer, delete or purge; the stream denies deletes and purges, and hosts write only after creating it with its exact config. Because any host can append to any sense subject, each event carries the ant's user JWT, an Ed25519 signature made with the ant's key, and the SHA-256 of the preceding event, appended with `Nats-Expected-Last-Subject-Sequence` ([architecture.md](architecture.md#stores-and-subjects)). Readers check position, hash chain, team-account signature for the ant (or an earlier name in `.sense/names` before `ant_renamed`), validity at store time, and absence of a prior `revoked.<U...>` entry in `ants_devices`; events imported from another bus verify against the prior accounts up to `through` once vouched for by a `log_imported` event signed on this bus ([config.md](config.md#senses-part)). A host lacking the ant's credentials can only append chain-breaking events (`ants doctor` reports breaks). A message a stream relayed onto a sense subject, or an answer the server stored there ([messages a stream relayed](#wire-acls-and-verification-invariants)), is no event: reads skip it, a run of them ending no read before the log's end, and an append finding only such messages after the last event it read expects the last of them instead; on unauthenticated servers events stay unsigned and check hash chain only.
- **Identities (`ants_identities`):** each ant's daemon puts and CAS-updates only `$KV.ants_identities.<ant>` (creating it on start, counting completed prompts, and settling the built-in `sense` id; [sense.md](sense.md#identity)); ants, assistants and humans direct-get all records, humans create the bucket and put single-token keys (`$KV.ants_identities.*`, `ants ant avatar`), and `ants auth revoke ANT` deletes the record. Shared settings (`$KV.ants_identities.*.settings`, [config.md](config.md#shared-settings)) are written only by host credentials and read by direct get. Because host credentials are not scoped per ant, each settings record is signed with the ant's key (carrying `credentials`, `signature`, `sequence` and `incarnation` over the ant, fields, machine, admin, time, target stream sequence and `_incarnation` marker `<sequence>@<RFC 3339 time>`), published with `Nats-Expected-Last-Sequence` besides key CAS. Readers (`ants daemon`, `ants ant show|set|export`) accept only records signed by an unrevoked (`ants_devices`), then-valid team JWT of that ant stored at `sequence` in the current `_incarnation`; replayed, cross-host or prior-incarnation records are ignored and re-signed by the daemon holding the ant's credentials from the settings it kept (or config on cold start). `ants init` writes `_incarnation` when absent, and `ants init --identities-restored` advances it after a backup restore (only humans write `_incarnation`, moving it strictly forward; buckets without it serve no shared settings). On unauthenticated servers records stay unsigned.
- **Trails (`ants_trails`, `ants_trail_runs`):** humans create both buckets; humans put and delete saved trails (`$KV.ants_trails.*`), and every user reads them by direct gets naming no subject, which list them too. A saved trail's key is its name, so no subject pins who saved it, and ant credentials (an assistant's too) neither put nor delete one: an ant asks `ants signer` on `ants.savetrail.<ant>` (`SaveTrailRequest` `{id, ant, requested_at, change: {op: save, trail, last?} | {op: remove, name, last}}`, core NATS, repeated every 2 s for up to 10 s) and hears the answer on `_INBOX.<ant>.savetrail` (`SaveTrailReply` `{request_id, ant, outcome: done|changed|refused}`), which only that ant reads. The signer (queue group `savetrail`, `Permissions::for_trail_keeper`) drops a request on another ant's subject, refuses a trail whose `saved_by` is not the asking ant or that fails a trail's bounds, refuses a `saved_from` unless the ant's own record of that run (`<ant>.<run>` in `ants_trail_runs`, read by direct gets naming no subject, as humans read it, past records a stream relayed onto the key) shows a finished run of an inline script that is the trail's, and saves only under a name the colony has no trail of or over a trail whose `saved_by` is the ant, removing only such a trail, each write expecting the revision the ant checked; a repeat of a change made already is answered `done`. So `saved_by: {kind: ant}` on a trail is that ant's, even against a harness holding its ant's `.creds`, and its `saved_from` a run whose record that ant keeps; such a harness writes its ant's run records too, so it can invent a finished run to name, but no other ant's run nor one whose script is not the trail's. A daemon without credentials, on an open server, makes the same checks itself. With authentication, `save_trail` and `remove_trail` therefore need a running `ants signer` (behind a leaf node, on a machine whose uplink has `--enroll-approver`). The ant's daemon also refuses both on an untrusted thread, which the signer cannot see: a harness asking the signer itself can save a trail as its ant's own from any thread, and such a trail still runs only as a saved trail runs, an untrusted run's step threads narrowed all the same ([trails.md](trails.md#trust)). A human saves and removes any. An assistant saves as itself, an ant, never as its human. Each ant's daemon, under the ant's credentials (an assistant's too), gets, puts and deletes only the records of the runs it conducts (`$KV.ants_trail_runs.<ant>.>`, and their direct gets naming the subject): no ant forges another conductor's (readers refuse a record a stream relayed there: [messages a stream relayed](#wire-acls-and-verification-invariants)), and none but an assistant, which also holds a human's reads of the bucket (its stream info and direct gets naming no subject), reads another conductor's. Humans, and `ants signer` to check a trail's source, read every run's records by direct gets naming no subject; humans list them by the stream info of both buckets, and write none (`ants chat` reads the steps on one thread by such a get filtered on `<ant>.on.<thread>.*`, the markers a conductor keeps of its steps under the thread of their run, rather than every step's marker): starting, stopping or resuming a run is a request to its conductor, which humans alone publish (`ants.trail.*`, a `TrailRequest`), the conductor's daemon alone hears on `ants.trail.<ant>` and answers on `ants.trailed.<ant>` (`TrailReply`); assistants send none, the request naming no one a daemon could check. A stop answer lists the steps to other ants still waiting, which the human's CLI withdraws (`<ant>.msg.<id>` in `ants_attempts`), as an ant marks only its own messages. Ants get no stream info of `ants_trail_runs`, and a consumer of it only filtering one of their own keys (`runsread-<ant>`, [trail buckets past relays](#wire-acls-and-verification-invariants)), so `<ant>.runs` lists a conductor's runs for its daemon. A `trail_step` on a message counts only where the conductor's own session record names the step's thread, so a forged one resolves nothing. Webhooks, observers, hosts and the channel manager reach neither bucket.
- **Trail tips (`ants_trail_tips`):** each ant, under its own credentials (an assistant's too), creates its own tips (`<trail>.<ant>.<id>`) and puts its own votes (`<trail>.<ant>.<writer>.<id>`), one subject covering both (`$KV.ants_trail_tips.*.<ant>.>`), and reads the whole bucket by direct gets naming no subject; readers skip an entry whose record does not match its key, so a tip's writer and a vote's voter are those its key names, and a vote by a tip's own writer counts for nothing. Humans create the bucket and read its stream info, write any key (`$KV.ants_trail_tips.>`), as `ants trail tips --retire` does to retire a tip under `<trail>._retired.<writer>.<id>`, which no ant's subject covers (`_` is in no ant's name) and which readers alone take a retirement from, so a tip's writer putting it again leaves it retired, and purge a trail's tips when removing the trail (`$JS.API.STREAM.PURGE.KV_ants_trail_tips`); an assistant does neither, so retiring and removing name a human. The daemon's checks (a trusted thread, a trail still saved, no vote on the ant's own tip, at most 200 live tips) bind only the daemon: a harness holding its ant's `.creds` writes under its ant's subject directly, from any thread, so it can leave tips on any trail ever saved and vote on any tip, as its ant; pass the 200 live tips, after which `leave_tip` refuses every ant until tips retire; and give a tip any id and date. Readers blunt the last: they take no tip or vote dated more than a minute ahead of their clock, so no date keeps a tip from ageing or retiring, and they tell tips apart by writer and id, so a tip reusing another's id draws none of its votes and a vote or `--retire` by id alone is refused while the id names two tips; and they count a vote only for the text it judged (its SHA-256 is in the vote), so a writer putting its tip again with other text keeps none of the votes cast on the earlier one. Such tips and votes still name the ant whose credentials wrote them, which `ants trail tips` shows, and a human retires them. Webhooks, observers, hosts and the channel manager reach none of it ([trails.md](trails.md#tips)).
- **Trail ratings (`ants_trail_ratings`):** each ant, under its own credentials (an assistant's too), puts only its own ratings (`$KV.ants_trail_ratings.*.<ant>.*`, a key `<trail>.<conductor>.<run>`), and reads the whole bucket by direct gets naming no subject; readers skip an entry whose record does not match its key, so a rating's conductor is the one its key names. Its daemon rates only runs it conducted, and from an untrusted thread only the run reporting on that thread; it rates only the trails still saved that the run took and those the ant itself saved from the run, and marks a rating of an untrusted run as such, which `find_trails` shows (a webhook's run is rated all the same, counting as any other). These checks bind only the daemon: a harness holding its ant's `.creds` puts ratings under its ant's key directly, so it can rate any trail under any number of invented runs, as its ant, with no untrusted mark. Readers take no rating dated more than a minute ahead of their clock, so no date keeps a rating at full weight; they cannot check a rating's run against its record, as no ant reads another conductor's runs and run records expire after 30 days while ratings stay. Such ratings still name the ant whose credentials put them, which `ants trail show NAME` shows. Humans create the bucket, read its stream info and every rating, write none, and purge a trail's ratings when removing the trail (`$JS.API.STREAM.PURGE.KV_ants_trail_ratings`); an assistant purges none. Webhooks, observers, hosts and the channel manager reach none of it ([trails.md](trails.md#rating-and-finding-trails)).
- **Read-only observers:** `Permissions::for_observer` allows only durable consumers `observe-{requests,decisions,dead}-<observer>` on `ANTS`, `ants.status.*.*`, `ants_colony` reads/watches, and self-renewal (see [hooks.md](hooks.md)).
- **Metadata verification:** daemons honour `owner` only for `human` or `ants_humans` members backed by channel posts or `ants_owners` (plus verified `origin_thread` chains in `ants_links`, max 32 hops), take `webhook: true` from the subject alone ([subject-pinned webhooks](#wire-acls-and-verification-invariants)), honour `rating_of` only on the conductor's own invitation to rate a trail run (from the ant to itself on the run's thread under the id of the run's end), and honour `on_behalf_of` only from the assistant the human's standing grant names whose record in `ants_devices` carries the human's `ants-assistant-of:` tag ([acting for its human](#acting-for-its-human)), never applying a decision made for a human without the human's signed confirmation or pre-allow rule ([confirming an assistant's acts](#confirming-an-assistants-acts)).
